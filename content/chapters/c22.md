# 成本工程与性能优化

前面二十多章都在讲"怎么让它跑起来、跑得对"。这一章讲一件同样决定项目生死、却最少被系统讨论的事：**怎么让它跑得起**。

## 先算清楚一笔账

Agent 的成本结构和普通 LLM 应用**完全不同**。差别来自一件事：

:::callout key 上下文是重复计费的
模型本身是无状态的。所以每一次调用，**你都要把整段历史重新发一遍**——而输入 token 是要付费的。
:::

假设一个 8 步的任务，每轮上下文增长如下：

| 轮次 | 输入 tokens | 说明 |
| --- | --- | --- |
| 1 | 2,400 | 系统提示 600 + 工具定义 1,400 + 问题 400 |
| 2 | 3,600 | 上一轮 + 一次工具结果 |
| 3 | 5,100 | 继续累加 |
| 4 | 6,600 | |
| 5 | 8,000 | |
| 6 | 9,200 | |
| 7 | 10,100 | |
| 8 | 10,800 | 该输出了 |
| **合计** | **≈ 55,800** | 而"有效信息"可能只有 3,000 |

**成本随步数近似二次增长**（步数 × 平均上下文长度）。这就是为什么第 5 章反复强调"能用 3 步解决就别设计成 10 步"——**减少步数不只是省延迟，是省平方级的钱**。

### 一个反直觉的结论

| 做法 | 单步效果 | 总成本 |
| --- | --- | --- |
| 用便宜模型，12 步做完 | 每步略差 | 可能更高 |
| 用贵模型，5 步做完 | 每步更好 | **通常更低** |

**别按"每百万 token 单价"选模型，要按"完成一个任务的总成本"选。** 一个贵一倍但步数少一半的模型，总成本往往更低——而且延迟和错误率也一起降了。

## 五个降本杠杆

按**投入产出比**排序，前两个通常能拿走 60% 以上的节省空间。

### 一、Prompt Caching —— 单笔收益最大

原理很简单：**如果每次请求的前缀完全相同，服务端可以复用已计算的 KV 缓存**，命中部分按很低的折扣计费。

看这张表就明白它为什么关键：

| 上下文组成 | 是否每轮变化 | 能否命中缓存 |
| --- | --- | --- |
| 系统提示 | 不变 | ✅ 命中 |
| 工具定义（Schema） | 不变 | ✅ 命中 |
| 长期记忆召回 | 每轮可能不同 | ❌ |
| 历史对话 | 每轮增长 | ⚠️ 前缀可命中 |
| 最新工具结果 | 每轮不同 | ❌ |

那些"不变的部分"（系统提示 + 工具定义）恰恰是**最大块的开销**。前面那张表里，1,400 token 的工具定义每一轮都要重发，8 轮就是 11,200 token——**如果它能命中缓存，这部分几乎白送**。

:::callout tip 让缓存真正生效的三条规则
1. **稳定内容必须放前缀**。系统提示、工具定义放最前；易变内容（时间戳、随机 ID、当前时间）绝不能混进去——**一个动态时间戳就能让整段前缀的缓存全部失效**。
2. **显式标记缓存断点**（多数供应商提供）。标记在"稳定块"的末尾，让系统知道从哪里可以复用。
3. **注意 TTL**。缓存通常只有几分钟有效期。高频场景收益巨大，一天跑几次的批处理几乎没有收益。

**最容易犯的错**：在系统提示里写"当前时间：{now}"。这一个字段会让缓存命中率掉到 0。
:::

### 二、分级模型路由 —— 第二个大头

不是每一步都需要最强的模型。把任务按"需要多少推理"分层：

| 环节 | 需要的模型 | 占比 |
| --- | --- | --- |
| 输入分类 / 意图识别 | 小模型 | 高 |
| 查询改写 | 小模型 | 高 |
| 工具选择（简单场景） | 小模型 | 中 |
| 多步推理 / 复杂规划 | **大模型** | 低 |
| 最终成文 | 中大模型 | 中 |

```python {3-9} title="分级路由：只在需要时用贵模型"
def pick_model(task: Task) -> str:
    if task.kind in ("classify", "rewrite", "extract"):
        return SMALL_MODEL          # 便宜 10~20 倍，质量足够
    if task.step_count <= 2 and task.tool_count <= 3:
        return MEDIUM_MODEL         # 简单任务不需要满血模型
    return LARGE_MODEL              # 只有真正难的推理才用
```

:::callout warn 一个常见的误判
"换小模型会降质"——**只对需要推理的环节成立**。

意图识别、查询改写、字段抽取这类任务，小模型和大模型的表现差异往往在噪声范围内，但成本差一个数量级。**先分级，再评估；不要一刀切。**
:::

### 三、上下文瘦身 —— 不动架构就能省

第 9 章讲过上下文预算，这里补上它的成本视角：

| 优化动作 | 典型节省 | 风险 |
| --- | --- | --- |
| 精简工具描述（去掉冗余示例） | 15~25% | 低 |
| 工具分组 / 动态注入（只给相关工具） | 20~35% | 低 |
| 历史对话滚动摘要 | 10~30% | 中（可能丢约束） |
| 工具结果结构化压缩 | 10~25% | 低 |
| 延迟加载（只放文档 ID，按需回查） | 15~40% | 低（多一次往返） |

**这几项可以叠加，且互不冲突。** 一个典型系统做完前四项，输入 token 常能降 40% 以上。

### 四、收敛步数 —— 省的是平方

| 手段 | 做法 |
| --- | --- |
| 提高规划质量 | 一次拆对，避免"规划—重规划"反复 |
| 并行化 | 无依赖的子任务并发执行（[第 6 章](#/chapter/c06)） |
| 早停 | 信息够了就停，不要"再确认一下" |
| 无进展检测 | 发现原地打转立刻中止（[第 5 章](#/chapter/c05)） |

### 五、缓存与批处理

| 手段 | 适用 | 典型命中率 |
| --- | --- | --- |
| **结果缓存** | 相同/相似查询 | 企业内部问答常 > 30% |
| 语义缓存 | 换个问法但意思相同 | 视场景，10~25% |
| 批处理 | 离线任务 | 多数供应商有折扣 |

:::callout danger 语义缓存的坑
"意思相同就返回缓存"听起来很美，但**边界很难把握**。

一个真实事故：客服系统把"退货期限是几天"和"退货**延长**期限是几天"判为同一语义，返回了错误答案。

**做法**：缓存键要么足够严格（完全一致 + 关键参数一致），要么在返回缓存结果前加一道轻量校验。宁可少命中，不要命中错的。
:::

## 量化：优化前后对比

以一个 8 步客服任务为例（数字为示意，请以你的实际账单为准）：

| 阶段 | 输入 tokens | 单任务成本 | 说明 |
| --- | --- | --- | --- |
| 基线 | ≈ 55,800 | 1.00× | 工具全部注入，历史全量，单一模型 |
| + 上下文瘦身 | ≈ 33,500 | 0.60× | 工具描述精简 + 结果压缩 |
| + Prompt Caching | ≈ 33,500（有效计费 ≈ 12,000） | **0.28×** | 稳定前缀命中缓存 |
| + 分级模型路由 | 同上 | **0.16×** | 简单环节换小模型 |
| + 减少步数（8→5） | ≈ 14,000（有效 ≈ 5,000） | **0.08×** | 规划收敛 + 早停 |

**从 1.00× 到 0.08×，架构没变，只是把每一层都做对了。**

:::callout key 优化的正确顺序
**先测量，再优化。** 顺序错了会浪费大量时间：

1. **先埋点**：把每一步的 `input_tokens` / `output_tokens` / 耗时记进 Trace（[第 14 章](#/chapter/c14)）
2. **找出占比最大的那一项**——通常是工具定义或历史对话
3. **从占比最大的开始改**，改完重新测量
4. 每次都记录"改前 / 改后"，没有数据支撑的优化不要合入

配套项目 `examples/support-agent` 里的 `agent/trace.py` 已经把这套埋点做好了，`summary()` 会直接输出单次任务的 token 与成本。
:::

## 省钱不能省掉质量

:::callout danger 三条不可逾越的红线
1. **护栏不能省**。安全校验、权限判断、高危动作审批——这些是确定性代码，本来就不花 token。
2. **评估不能省**。省掉评估等于闭眼开车，你根本不知道省下来的是成本还是质量。
3. **引用的上下文不能省**。压缩历史可以，但不能把"用户明确提出的约束"压掉——那会导致答非所问，用户重问一遍的成本远高于省下的 token。
:::

降本的正确姿态是**降级而不是失败**：

```python {2-6} title="预算耗尽时降级，而不是报错"
def on_budget_exhausted(ctx):
    if ctx.budget_used > 0.9:
        # 降到单轮 RAG：不再走多步循环，直接检索引擎 + 一次生成
        return fallback_single_call(ctx)
    return "抱歉，本次处理超出预算，已为你转接人工。"
```

**用户能接受"简单一点的回答"，不能接受"系统挂了"。**

## 成本监控：三层预算 + 两个归一化指标

```python {2-5} title="三层预算（缺一不可）"
BUDGET_PER_RUN      = 80_000       # 单次任务：防止单个请求失控
BUDGET_PER_USER_DAY = 2_000_000    # 单用户日累计：防止异常使用
BUDGET_GLOBAL_HOUR  = 50_000_000   # 全系统小时熔断：防止故障放大
```

光看总额没意义，要盯**归一化指标**：

| 指标 | 为什么重要 |
| --- | --- |
| **每任务成本** | 直接反映效率；涨了说明步数或上下文在膨胀 |
| **每解决成本** | 成本 ÷ 自助解决数；这才是真正的单位经济性 |
| 缓存命中率 | 掉下来说明前缀被污染了（常见：混入了动态字段） |
| 小模型占比 | 分级路由是否真的在生效 |

:::callout warn 最常见的成本事故
**不是模型太贵，而是某个字段让缓存全部失效。**

把"当前时间""请求 ID""会话 UUID"这类动态值写进系统提示或工具定义的**前缀**，缓存命中率会直接归零，成本悄悄涨 3~5 倍，而且在总账单上很难察觉。

**排查方法**：单独监控缓存命中率，并对前缀内容做快照对比。
:::

## 本章要点

- Agent 成本随步数**近似二次增长**，因为上下文每轮都要重发。**减少步数是平方级的省钱。**
- **按"完成一个任务的总成本"选模型**，不要按单价选。
- 五个杠杆：**Prompt Caching > 分级模型路由 > 上下文瘦身 > 收敛步数 > 结果缓存**。
- 缓存生效的前提是**稳定内容放前缀，且前缀里不能有动态字段**——这是最常见的成本事故。
- 红线：**护栏、评估、用户明确约束不能省**；预算耗尽要降级而不是失败。
- 监控要盯**每任务成本**与**每解决成本**，而不只是总花费。
- **先埋点、再优化、每步留数据。**
