# 案例二：代码助手 Agent

代码助手是少数**拥有客观成功判据**的 Agent 场景——**测试能不能跑通**。这让它可以做一件其他场景很难做的事：**自动自我修正**。

## 核心优势：可验证性

| 场景 | 成功判据 | 能否自动验证 |
| --- | --- | --- |
| 客服 | 用户满意 | 难 |
| 写作 | 质量好坏 | 难 |
| **代码** | **测试通过 / 编译通过 / 类型检查通过** | **能** |
| 数据分析 | 结果正确 | 部分（可交叉验证） |

:::callout key 可验证性带来的根本差异
因为能自动判断成败，代码助手可以进入一个**确定性的改进循环**：

```text
写代码 → 跑测试 → 失败 → 读取错误信息 → 修正 → 跑测试 → …
```

这个循环的每一步都有**明确的信号**，不依赖 LLM 的自我评价。**这是 Agent 设计中"能验证就别让模型自评"原则的最佳示范。**
:::

## 三段式架构

```text
① 检索阶段（理解上下文）
   - 找到相关文件（不是整个仓库）
   - 理解项目约定、依赖、已有模式
        ↓
② 编辑阶段（生成变更）
   - 生成 patch，而不是整文件重写
   - 逐文件应用，可回滚
        ↓
③ 验证阶段（确认正确）
   - 语法检查 → 类型检查 → 单元测试 → 集成测试
   - 失败则带着错误信息回到编辑阶段
```

:::callout warn 最常见的失败：跳过检索阶段
直接让模型"写一个功能"，它会**发明一套与项目约定不符的写法**——用了项目里没有的库、命名风格不一致、重复实现了已有的工具函数。

**检索阶段的价值不是"找代码"，而是"让模型学会这个项目的说话方式"。**
:::

## 检索阶段：如何高效找到相关代码

仓库可能很大，不可能全塞进上下文。

```python {2-11} title="分层检索策略"
def gather_context(task: str, repo: Repo) -> Context:
    ctx = Context()
    # 1. 语义检索：按任务描述找相关文件片段
    ctx.snippets = vector_search_code(task, top_k=8)
    # 2. 符号检索：找相关的函数/类定义（精确）
    for sym in extract_symbols(task):
        ctx.definitions += repo.find_definition(sym)
        ctx.usages += repo.find_references(sym)[:5]     # 看别人怎么用的
    # 3. 结构信息：目录树（压缩后）+ 关键配置文件
    ctx.tree = repo.tree(depth=3, exclude=["node_modules", "dist", ".git"])
    ctx.config = repo.read(["package.json", "tsconfig.json", "README.md"])
    # 4. 约定发现：找同类实现的既有范例
    ctx.examples = find_similar_implementations(task, repo, k=2)
    return ctx
```

:::callout tip 三个高价值细节
1. **找"同类范例"**。让模型照着项目里已有的类似实现写，风格一致性会显著提升。这是投入产出比最高的检索动作。
2. **找"调用点"**。知道函数被谁调用、怎么调用的，比只知道函数签名有用得多。
3. **读配置文件**。`package.json` / `tsconfig.json` / lint 规则能立刻约束模型不要发明新依赖。
:::

## 编辑阶段：patch 优于整文件重写

```python {2-10} title="编辑工具的设计"
tools = [
    read_file(path, start, end),          # 分段读取，避免大文件撑爆上下文
    search_code(pattern, glob),           # 正则/语义搜索
    apply_patch(path, old_str, new_str),  # 精确替换（要求 old_str 唯一）
    create_file(path, content),
    run_command(cmd, timeout),            # 沙箱内执行
    run_tests(target),                    # 专门的测试工具，返回结构化结果
]
```

:::callout danger 为什么不用"整文件重写"
1. **上下文成本**。一个 800 行的文件重写一遍，输入输出都是几千 token。
2. **破坏性**。模型可能在重写时"顺手"改动不相关的部分，引入难以察觉的回归。
3. **不可审计**。patch 能看清改了哪几行，整文件重写看不出。

**`apply_patch` 要求 `old_str` 在文件中唯一**，这个约束能防止模型改错位置——不唯一时工具报错，让模型提供更多上下文，这是一个很好的自我纠正机制。
:::

## 验证阶段：错误信息驱动自我修正

这是代码助手最值得学习的地方——**把测试输出当作反馈信号**：

```python {3-13} title="验证驱动的修正循环"
def solve(task, repo, max_attempts=4):
    context = gather_context(task, repo)
    patch = llm_generate_patch(task, context)

    for attempt in range(max_attempts):
        result = apply_and_test(patch)          # 应用 + 跑测试
        if result.all_passed:
            return Success(patch)

        # 关键：把结构化的失败信息喂回去
        context += feedback(
            failing_tests=result.failed_names,       # 哪些测试挂了
            error_message=result.error[:2000],       # 具体错误（截断防爆上下文）
            diff=result.diff,                        # 当前改动
            hint="请只修正导致失败的部分，不要重写整个文件。"
        )
        patch = llm_revise_patch(task, context)

    return Failure(patch, result)   # 超过尝试次数，交给人
```

:::callout key 三个设计要点
1. **反馈信息要结构化**：失败的测试名、错误信息、当前 diff 分开传，比丢一大段日志有效得多。
2. **明确要求"最小修正"**。否则模型每次失败都会大改一遍，越改越乱。
3. **设置尝试上限（3~5 次）**。超过就应该交给人，而不是无限重试。
:::

## 沙箱：不可协商的前提

:::callout danger 代码执行必须在沙箱里
Agent 生成的代码要被执行——这意味着它能做任何事：读文件、发网络请求、删数据。

**必须的隔离措施**：
- 容器隔离，无宿主机文件系统访问（或只挂载工作目录）
- 网络出口白名单（默认禁网）
- CPU / 内存 / 执行时间硬限制
- 非 root 用户运行
- 一次性环境，用完即销毁
- **危险命令黑名单**（`rm -rf /`、`curl | sh`、写 `/etc` 等）

**不要因为"只是跑个测试"就跳过隔离。** 测试脚本本身也是代码。
:::

## 完整流程示例

```text title="一次真实的任务执行"
任务：把 /api/users 接口的分页参数从 page/size 改成 cursor

[检索] 找到：routes/users.ts、services/userService.ts、
              tests/users.test.ts、types/pagination.ts
       发现既有范例：其他 3 个接口已使用 cursor 分页（照着改）

[编辑] 1. types/pagination.ts   新增 CursorPagination 类型
       2. services/userService.ts 改写查询逻辑（复用已有的 buildCursorQuery）
       3. routes/users.ts        更换参数解析
       4. tests/users.test.ts    更新测试用例

[验证] ✓ 类型检查通过
       ✗ users.test.ts: "should paginate with cursor" 失败
         期望 10 条，实际 9 条（末页边界处理错误）

[修正] 修改 userService.ts 第 42 行的边界判断
       ✓ 全部测试通过

[交付] 4 个文件的 patch + 测试结果 + 改动说明
```

## 效果指标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 一次通过率 | ≥ 50% | 无需修正循环 |
| 最终通过率（≤4 次尝试） | ≥ 85% | 修完能过 |
| 平均尝试次数 | ≤ 1.8 | 反映反馈质量 |
| 最小改动率 | ≥ 90% | 改动行数 / 总行数 |
| 无回归率 | ≥ 98% | 未破坏既有测试 |

:::callout tip "最小改动率"是被忽视的关键指标
如果 Agent 每次都要改 200 行才能完成任务，即便测试通过了，代码评审的负担也会让团队放弃使用它。

**让 Agent 写"小 diff"，比让它写"能跑的代码"更重要。** 这也是"要求最小修正"这条提示词约束存在的意义。
:::

## 本章要点

- 代码助手的核心优势是**可验证性**：测试结果是客观信号，能驱动自动修正循环。
- 三段式：**检索（理解项目约定）→ 编辑（生成 patch）→ 验证（跑测试）**。
- 检索要分层：**语义片段 + 符号定义 + 调用点 + 同类范例 + 配置文件**；"找同类范例"收益最高。
- 编辑用 **patch 而非整文件重写**；`old_str` 唯一性约束能防改错位置。
- 验证循环要把**失败的测试名 + 错误信息 + 当前 diff** 结构化回灌，并要求最小修正，上限 3~5 次。
- **代码执行必须在沙箱**，这不是可选项。
