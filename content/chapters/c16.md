# 案例一：智能客服 Agent

客服是 Agent 落地最密集的场景，因为它天然满足三个条件：**任务路径不固定、有大量文档可检索、效果可量化**。

## 业务目标与约束

先明确目标，否则会做成一个"什么都能聊但什么都办不成"的玩具：

| 目标 | 指标 | 约束 |
| --- | --- | --- |
| 解决常见问题 | 自助解决率 ≥ 70% | 不能编造政策 |
| 降低转人工量 | 转人工率下降 ≥ 30% | 必须能一键转人工 |
| 保护用户数据 | 零数据泄露 | 只能查本人数据 |
| 响应速度 | P95 < 5 秒 | 首响 < 2 秒 |

:::callout key 客服 Agent 的第一原则
**宁可转人工，也不要猜。** 客服场景的错误成本很高（说错政策可能导致投诉、赔付），所以置信度阈值要设得保守。

"我不知道"是一个合格的回答；"我猜是……"是不合格的回答。
:::

## 架构

```text
用户消息
  → [输入护栏] 注入检测 / 情绪识别 / 越权意图
  → [意图路由] 三类分流
       ├─ 政策咨询 → RAG 检索知识库 → 生成带引用的回答
       ├─ 订单操作 → 工具调用（查订单 / 申请退款 / 改地址）
       └─ 投诉/超范围 → 转人工
  → [输出护栏] PII 脱敏 / 政策一致性校验
  → 回复用户
```

关键在于**分流要早**。把简单咨询和需要动作用的请求分开处理，能大幅降低成本：

| 分流 | 处理方式 | 平均成本 |
| --- | --- | --- |
| 政策咨询 | RAG 单轮 | 1 次调用 |
| 订单操作 | Agent 循环（2~4 步） | 3~5 次调用 |
| 投诉/超范围 | 直接转人工 | 0 次调用 |

## 知识库设计

客服知识库的质量直接决定效果。三个关键设计：

### 一、文档结构要面向检索

```markdown title="✅ 好的知识库文档结构"
# 退换货政策

## 适用条件
- 商品签收后 7 天内
- 商品未使用、包装完整
- 生鲜、定制类商品不支持

## 操作步骤
1. 进入「我的订单」→ 找到对应订单 → 点击「申请退货」
2. 填写退货原因，上传商品照片
3. 审核通过后 24 小时内预约上门取件

## 常见问题
Q：超过 7 天还能退吗？
A：超出 7 天原则上不支持，如属商品质量问题，可在 15 天内申请，需附带质检报告。

Q：运费谁承担？
A：非质量问题的退货运费由用户承担（8 元/单）；质量问题由平台承担。
```

:::callout warn 客服知识库的三个反模式
1. **一篇文档包罗万象**（5000 字以上）。检索时只能召回整篇，噪声极大。→ 按主题拆分，每篇聚焦一个问题。
2. **表格化的政策**（一堆字段堆在一起）。→ 转成自然语言问答对，更容易被检索和理解。
3. **只写"是什么"不写"怎么办"**。→ 每个政策都要有明确的操作步骤，否则 Agent 无法引导用户。
:::

### 二、给每个知识块加上"有效期"

政策会变。**召回过期政策比召回不到更危险**：

```python {2-7} title="带版本与时效的知识块"
{
    "chunk_id": "KB-RETURN-004",
    "text": "非质量问题的退货运费由用户承担（8 元/单）",
    "policy_version": "v3.2",
    "effective_from": "2026-06-01",
    "effective_to": None,            # None 表示仍生效
    "supersedes": "KB-RETURN-002",
}
```

检索时强制过滤：`WHERE effective_to IS NULL OR effective_to > now()`。

### 三、多轮提问的消解

客服对话常常是碎片化的：

```text title="真实的多轮对话"
用户：我这个能退吗
Agent：请问是哪笔订单呢？
用户：就是上周那个
Agent：找到了 8 月 28 日的订单（订单号 ...0417，商品：蓝牙耳机）。
      该商品属于普通商品，签收 7 天内可退，您目前还在期限内。
```

:::callout tip 关键做法：把指代消解结果写进会话记忆
`"我这个"` → `订单 ...0417`。这个映射必须写入会话记忆，否则后续每一轮都要重新追问。

这也是"会话记忆要用结构化状态"的一个具体体现（第 7 章）：
```json
{"resolved_refs": {"我的订单": "ORD-20260828-0417"}, "topic": "退货政策"}
```
:::

## 工具设计

客服 Agent 需要一组精心设计的工具。注意**每个工具都做了权限收敛**：

```python {2-12} title="客服工具集（只读优先，写操作需确认）"
tools = [
    # 只读：无副作用，可自由调用
    get_order(user_id, order_id),          # 内部强制校验 order.user_id == user_id
    get_logistics(order_id),
    search_knowledge_base(query, top_k=3),

    # 写操作：需要二次确认
    request_refund(order_id, reason, idempotency_key),   # 幂等键防重复提交
    update_shipping_address(order_id, new_address, confirm),

    # 转人工
    transfer_to_human(reason, context_summary),
]
```

:::callout danger 三个必须做对的细节
1. **`get_order` 内部强制校验归属**。不能只靠提示词说"只能查自己的订单"——工具实现里必须再校验一次 `order.user_id == ctx.user.id`。
2. **写操作必须幂等**。用户说"申请退款"两次，不能产生两个退款单。用 `idempotency_key`（可以是 `order_id + user_id + 日期`）来保证。
3. **写操作前二次确认**。Agent 应先复述动作给用户确认（"我将为订单 ...0417 申请退款，金额 299 元，确认吗？"），确认后才执行。
:::

## 转人工策略

什么情况下必须转人工？用规则显式定义，不要让模型自由判断：

```python {2-9} title="转人工的触发条件"
def should_transfer(state) -> bool:
    return any([
        state.user_sentiment < -0.5,           # 情绪激烈
        state.turns_without_progress >= 2,     # 连续两轮没进展
        state.confidence < 0.6,                # 置信度低
        state.mentions_legal,                  # 提及投诉/法律/监管
        state.amount_involved > 1000,          # 涉及金额较大
        state.user_explicitly_asks,            # 用户明确要求人工
    ])
```

:::callout warn 用户情绪是最高优先级信号
用户在第二次表达不满时就应该转人工，而不是等他说出脏话。**情绪识别要独立于业务流程**，作为一条旁路信号始终生效。
:::

### 转人工要"带着上下文转"

```text title="生成的工单内容"
【用户诉求】订单 ...0417 的蓝牙耳机想退货，但不确定是否在期限内
【Agent 已完成】
  - 已定位订单：ORD-20260828-0417，签收日 2026-08-30
  - 已确认政策：普通商品 7 天内可退（政策版本 v3.2）
  - 已告知用户：仍在期限内，可自助申请
【转人工原因】用户情绪不满（连续 2 次表达"太麻烦了"）
【建议动作】协助用户完成退货申请，或说明上门取件流程
```

## 效果指标与优化顺序

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 自助解决率 | 未转人工且用户未追问的会话占比 | ≥ 70% |
| 首轮解决率 | 一轮对话内解决的占比 | ≥ 45% |
| 政策准确率 | 回答与最新政策一致的占比（抽检） | ≥ 98% |
| 转人工率 | 转人工会话占比 | 相对基线下降 30% |
| 平均轮次 | 解决问题所需的对话轮数 | ≤ 3 |

:::callout key 优化顺序（按投入产出比）
1. **知识库质量**（切分、有效期、问答化）—— 收益最大，成本最低
2. **意图路由准确率** —— 分流错了，后面全错
3. **转人工策略** —— 减少无效对话，提升用户满意度
4. **回复语气与结构** —— 影响观感，但不影响解决率
5. **模型升级** —— 收益最小，成本最高

**大多数团队反着做，先换模型。**
:::

## 踩坑记录

| 坑 | 现象 | 解决 |
| --- | --- | --- |
| 知识库有重复文档 | 召回一堆相似内容，回答糅杂了不同版本的政策 | 入库时做去重 + 版本管理 |
| 只给模型看摘要 | 回答正确但无法指导操作 | 保留操作步骤的完整内容 |
| 没有幂等保护 | 用户重复点击产生重复退款 | 加幂等键 |
| 转人工不带上下文 | 用户向人工重复描述，体验差 | 生成结构化工单 |
| 提示词里写"不要编造" | 仍会编造 | 改为**强制引用** + 无引用时明确说"资料未涵盖" |

## 本章要点

- 客服 Agent 的第一原则：**宁可转人工，也不要猜**。
- 早分流：**政策咨询（RAG）/ 订单操作（Agent 循环）/ 超范围（转人工）** 三类分开处理。
- 知识库三要点：**结构化拆分、带有效期、问答化**。
- 工具设计：**只读优先、内建权限校验、写操作幂等 + 二次确认**。
- **转人工用规则显式定义**，情绪识别作为旁路信号；转人工必须带上下文。
- 优化顺序：知识库 > 路由 > 转人工策略 > 语气 > 模型。
