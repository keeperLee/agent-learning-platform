# 从脚本到 Agent：能力演进

理解演进史不是为了怀旧，而是为了一个很实际的目的：**当下一次有人向你推销"全新 Agent 范式"时，你能判断它新增的到底是哪一级能力。**

## 四级演进

把「决策权」作为标尺，AI 系统的演进可以清晰地切成四级。每一级都从上一级手里接管了一部分决策权：

| 级别 | 决策来源 | 适应变化 | 人的角色 |
| --- | --- | --- | --- |
| L1 规则程序 | 人写死的 if/else | 不能，改需求就要改代码 | 编写规则 |
| L2 机器学习 | 从数据中学到的模型 | 能泛化到相似样本 | 标注数据、调参 |
| L3 LLM 应用 | 模型按固定流程填空 | 能理解自然语言、处理模糊输入 | 设计提示与流程 |
| **L4 Agent** | **模型自己决定下一步** | **能在开放环境中探索新路径** | **定义目标与边界** |

注意「人的角色」这一列的变化：从**编写规则**，到**标注数据**，到**设计提示**，再到**定义目标与边界**。人负责的粒度越来越粗，但要求的抽象能力越来越高。

:::callout key 一个判断技巧
看到任何号称"能力跃迁"的技术，先问一句：**它接管了哪一部分决策权？** 如果控制流仍然由人写死的代码决定，那它属于 L3，无论包装成什么名字。
:::

## 从 L1 到 L2：学会"泛化"

L1 的典型形态是这样的：

```python {4-7} title="L1 · 规则程序"
def answer_question(text):
    text = text.lower()
    # 规则是人穷举出来的，覆盖不到的情况直接失败
    if "退货" in text:
        return "退货请在订单页申请，7 天内无理由。"
    elif "运费" in text:
        return "满 99 元包邮，否则 8 元。"
    else:
        return "抱歉，我没有理解您的问题。"
```

问题显而易见：`else` 分支会吞掉一切没被穷举的输入。L2 用统计学习解决了泛化问题——模型从标注数据里学到了「相似问法应该给相似答案」，不再需要人工穷举。

但 L2 有个天花板：**它只能做"分类"和"打分"，无法生成结构化的复杂输出，也无法调用外部系统**。

## 从 L2 到 L3：学会"理解与生成"

LLM 带来了两个质变：

1. **自然语言接口**。不需要再为每种意图写规则，提示词就是接口。
2. **零样本迁移**。没见过的任务，描述一遍就能做。

于是有了 RAG（检索增强生成）这种经典 L3 形态：

```python {3-6} title="L3 · RAG 问答（控制流由代码写死）"
def rag_answer(question):
    # 流程是固定的三步，模型只在最后一步参与
    docs = vector_search(question, top_k=5)          # 1. 检索
    prompt = build_prompt(docs, question)            # 2. 拼提示词
    return llm.generate(prompt)                      # 3. 生成
```

这段代码里，**控制流完全由人决定**：永远是「检索 → 拼提示 → 生成」这三步。如果第一次检索没找到相关内容，它不会换个关键词再试一次——因为代码没写这个分支。

:::callout info RAG 不是 Agent
RAG 是 L3。它很有效，但它的流程是固定的。当问题模糊、需要多轮澄清、或者需要根据检索结果决定下一步查什么时，L3 就撑不住了——这正是 L4 要解决的问题。
:::

## 从 L3 到 L4：学会"自己找路"

把上面那段 RAG 改成 Agent 形态，代码结构会发生本质变化：

```python {6-12} title="L4 · Agent（控制流交给模型）"
def agent_answer(question):
    messages = [system_prompt(), user(question)]
    for step in range(MAX_STEPS):                    # 由模型决定循环内容
        reply = llm.chat(messages, tools=TOOLS)
        if not reply.tool_calls:                     # 模型认为可以回答了
            return reply.content
        for call in reply.tool_calls:                # 模型自己选了哪个工具、什么参数
            result = execute(call)
            messages.append(tool_result(call.id, result))
    return "任务超出步数上限，已中止"
```

对比 L3 的版本，最关键的差异是：**再也没有"先检索再生成"这种写死的顺序**。模型可能检索三次，可能先查数据库再检索，也可能直接回答——路径是运行时才生成的。

## 演进带来的新问题

每一次决策权的转移，都会引入一类新问题。这张表在后续章节会反复用到：

| 演进 | 新增能力 | 新增问题 | 对应章节 |
| --- | --- | --- | --- |
| L1 → L2 | 泛化 | 数据偏差、不可解释 | — |
| L2 → L3 | 理解与生成 | **幻觉**（生成得很流畅但内容是错的） | 第 4 章 |
| L3 → L4 | 自主决策 | **错误累积、成本失控、不可复现** | 第 4、14 章 |

:::callout warn 为什么"错误累积"是 Agent 特有的
L3 只有一次模型调用，出错就是一次错误。L4 有 N 次调用，如果单步成功率是 95%，10 步之后的整体成功率只有 `0.95¹⁰ ≈ 60%`。这就是为什么 Agent 工程的重心不在"让单步更强"，而在"**让多步不出致命错误**"——手段包括重试、校验、回滚、人工兜底。第 4 章会展开算这笔账。
:::

## 你应该从这一章带走什么

1. **分级看能力**。任何新技术先归类到 L1~L4，判断它接管了哪部分决策权。
2. **警惕伪 Agent**。控制流仍写死在代码里的，就是 L3。
3. **能力有代价**。接管决策权 = 引入不确定性。L4 的所有工程实践，本质上都是在**把不确定性关进笼子**。

下一章我们把镜头推到最近处，看看 Agent 的"大脑"到底强在哪、弱在哪——只有先理解它的固有短板，才能理解后面那些架构设计为什么长成那样。
