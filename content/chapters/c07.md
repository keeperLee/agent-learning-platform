# 记忆机制

模型是**无状态**的——每一次调用它都从零开始。所以 Agent 所谓的"记忆"，完全是应用层用工程手段造出来的。

这一章讲清楚三件事：**记忆分几层、什么信息该写进去、什么时候该忘掉。**

## 三层记忆

:::diagram memory caption="图 7-1 · 记忆分层：越靠上越快越贵，越靠下越慢越持久"
:::

| 层级 | 载体 | 容量 | 生命周期 | 访问成本 |
| --- | --- | --- | --- | --- |
| **工作记忆** | 上下文窗口 | 极小（几十 K token） | 单次调用 | 高（按 token 计费） |
| **会话记忆** | 任务状态对象 / 摘要 | 小 | 单次任务 | 低 |
| **长期记忆** | 向量库 / KV / 图数据库 | 大 | 跨会话 | 中（需检索） |

:::callout key 记忆设计的核心矛盾
**工作记忆很贵，长期记忆很慢。** 所以记忆系统的全部设计工作，可以概括成一句话：

> **在正确的时刻，把正确的信息，从慢的地方搬到快的地方。**

这就是"写入策略"（什么时候把信息搬到慢的地方存起来）和"检索策略"（什么时候从慢的地方取回来）要做的事。
:::

## 工作记忆：上下文就是 RAM

工作记忆不是"存"出来的，而是**每轮重新组装**出来的：

```python {2-7} title="工作记忆的组装"
def working_memory(state):
    return [
        system(SYSTEM_RULES),                  # 固定开销
        *recall_long_term(state.goal),         # 长期记忆召回（按相关性）
        *recent_turns(state.history, n=4),     # 最近若干轮原文
        summary(state.history[:-4]),           # 更早的部分压成摘要
        system(f"当前目标：{state.original_goal}"),   # 目标锚定（放末尾）
    ]
```

注意最后一行：**把目标放在上下文末尾**，利用"开头和结尾信息利用率更高"的位置效应，这是对抗跑偏最廉价的手段。

## 会话记忆：记住"任务进行到哪了"

会话记忆存的不是对话原文，而是**结构化状态**。这是 Agent 与聊天机器人最大的实现差异：

```python {1-9} title="会话记忆的典型结构"
{
  "goal": "分析 Q3 销售下滑原因并给出建议",
  "plan": ["t1", "t2", "t3", "t4", "t5"],
  "done": ["t1", "t2"],
  "facts": [
    "Q3 总 GMV 2864 万，环比 -12.3%",
    "下滑主要来自华东区（-21%），其他区域基本持平",
    "华东区下滑集中在 8 月中旬之后"
  ],
  "open_questions": ["8 月中旬华东区发生了什么？"],
  "artifacts": { "chart_url": "...", "data_file": "..." }
}
```

:::callout tip 为什么要用结构化状态而不是聊天历史
1. **省 token**：50 轮对话原文可能 30K token，结构化状态只有 300。
2. **抗漂移**：`facts` 是已被确认的结论，不会被后续对话中的假设污染。
3. **可干预**：人可以修改某条 fact 来纠正 Agent 的认知。
4. **可恢复**：任务中断后可以从状态直接续跑，无需重放对话。
:::

:::callout warn 一个高频 bug
**把"模型的推测"写进 `facts`。** 一旦某个未经验证的结论被当作事实存储，后续所有推理都会建立在它之上，且再也无法自我纠正。

正确做法：`facts` 只接受**有工具结果支撑**的条目，并记录来源 ID。模型自己的推测放进 `hypotheses`，并在提示词里明确区分。
:::

## 长期记忆：三种不同的存储形态

不是所有"长期记忆"都是向量库。按用途分，至少有三类：

| 类型 | 存储 | 典型内容 | 检索方式 |
| --- | --- | --- | --- |
| **语义记忆** | 向量库 | 知识、文档、历史结论 | 相似度检索 |
| **情节记忆** | 事件流 / KV | 过去发生过的任务与结果 | 关键词 + 时间过滤 |
| **实体记忆** | 图数据库 / 结构化表 | 用户画像、组织关系、偏好 | 精确查询 + 关系遍历 |

## 写入策略：什么值得存

记忆库最大的敌人是**垃圾信息堆积**。存得越多，检索信噪比越低。下面是一套实用的过滤规则：

```python {4-11} title="记忆写入过滤器"
def should_remember(item, context):
    if len(item.text) < 12:                       # 太短，信息量不足
        return False
    if item.source != "tool" and item.confidence < 0.8:
        return False                              # 无工具支撑且置信度低 → 不存
    if is_greeting_or_smalltalk(item.text):
        return False                              # 寒暄不入库
    if exists_similar(item, threshold=0.92):      # 已有近义记忆 → 合并而非新增
        return merge_with_existing(item)
    return item.importance(item.text) >= 0.5      # 重要性打分
```

**重要性打分**可以交给模型（一次便宜的调用），也可以用启发式规则：

| 信号 | 权重 | 说明 |
| --- | --- | --- |
| 用户显式表达（"记住…"、"以后都…"） | +++ | 最强的写入信号 |
| 用户偏好与纠正（"不对，应该是…"） | +++ | 高价值，往往直接影响后续所有交互 |
| 有工具结果支撑的事实 | ++ | 可信度高，可复用 |
| 任务结论 | ++ | 值得沉淀 |
| 中间过程细节 | − | 一般不值得存 |

:::callout info 一个被忽略的写入来源
**用户的纠正往往是最有价值的记忆。** 当用户说"不对，我们公司的口径是不含税"时，这条信息应该被立刻写入长期记忆，并带有高优先级——因为它能防止同一个错误在后续所有会话中重复发生。
:::

## 检索策略：怎么取回来

**朴素做法**是纯向量相似度 Top-K。但生产环境通常需要叠加几层过滤：

```python {2-8} title="多级过滤的检索"
def recall(query, user, k=5):
    candidates = vector_search(query, top_k=k * 4)       # 1. 先多召回一些
    candidates = filter_by_scope(candidates, user)       # 2. 权限/租户隔离（必须）
    candidates = filter_by_freshness(candidates, days=180)  # 3. 时效过滤
    ranked = rerank(query, candidates)                   # 4. 重排（比纯向量更准）
    ranked = dedupe(ranked, threshold=0.9)              # 5. 去重
    ranked = apply_decay(ranked, half_life_days=90)      # 6. 时间衰减加权
    return ranked[:k]
```

:::callout warn 第 2 步不是可选项
权限过滤必须在**检索阶段**完成，而不是拿到结果后再过滤。原因有两个：① 未过滤的内容可能已经进入模型上下文，存在泄露风险；② 过滤后结果可能不足 K 条，需要重新检索。

**在多租户系统里，记忆检索不带租户过滤是一个严重的安全缺陷。**
:::

### 时间衰减

记忆的价值随时间下降，但不同类型的记忆衰减速度不同：

```python {3-6} title="衰减权重"
def apply_decay(items, half_life_days=90):
    for it in items:
        age = (now() - it.created_at).days
        decay = 0.5 ** (age / half_life_days)
        # 用户偏好衰减慢，临时事实衰减快
        it.score *= decay if it.type == "fact" else (0.9 ** (age / 30))
    return items
```

## 遗忘：比记忆更难的设计

一个不会遗忘的系统，最终会变成一个什么都记不住的系统——因为检索被噪声淹没了。

| 遗忘策略 | 触发条件 | 做法 |
| --- | --- | --- |
| **时效淘汰** | 超过 T 天未被召回 | 降权或归档 |
| **冲突消解** | 新记忆与旧记忆矛盾 | 标记旧记忆为失效（**不要物理删除**） |
| **容量压缩** | 每类记忆超过 N 条 | 聚类合并为一条概括性记忆 |
| **人工清理** | 用户主动删除 | 硬删除 + 清理索引 |

:::callout danger 冲突消解必须保留历史
当用户说"我们改用 Postgres 16 了"，旧记忆"使用 Postgres 15"不能用 `DELETE` 删掉，而应标记 `superseded_by`。原因：

- 历史任务的分析可能仍需要旧结论；
- 出错时你需要知道"模型当时是基于什么信息做的判断"；
- 用户可能反悔（"改回 15 了"）。

**记忆的正确操作是"追加 + 标记"，而不是"覆盖"。**
:::

## 本章要点

- 记忆分三层：**工作记忆（贵而快）、会话记忆（结构化状态）、长期记忆（大而慢）**。核心工作是把信息在正确的时刻搬对地方。
- 会话记忆要用**结构化状态**，而不是聊天原文；`facts` 只存有工具支撑的结论，推测另置 `hypotheses`。
- 长期记忆分**语义/情节/实体**三类，检索要叠加**权限、时效、重排、去重、衰减**五层过滤。
- **权限过滤必须在检索阶段完成**，否则是安全缺陷。
- 遗忘与记忆同等重要：**追加 + 标记失效**，而不是覆盖删除。
