# 编排框架选型

框架能省时间，也能锁死你。这一章给出一张尽量客观的对比表和一套决策方法。

## 框架提供的价值

先明确框架到底帮你做了什么，才知道该不该用：

| 能力 | 自己实现的成本 | 框架的价值 |
| --- | --- | --- |
| 模型适配 | 每个供应商写一遍 | ★★★ 统一接口，换模型只改配置 |
| 工具注册与 Schema 生成 | 中等 | ★★★ 从函数签名自动生成 Schema |
| 循环与状态管理 | 中等 | ★★★ 尤其是有环/分支的流程 |
| 持久化与断点续跑 | **高** | ★★★★ 生产必备，自己写很费劲 |
| 流式输出 | 中等 | ★★ 已封装 |
| 可观测 / Trace | **高** | ★★★★ 接入现有平台即可 |
| 人机协同（中断/审批） | **高** | ★★★ 需要状态快照支持 |

:::callout key 判断该不该用框架的两个问题
1. **你的流程有分支、有环、需要持久化吗？** 如果只是"提示 → 工具 → 提示"的直线，框架的收益很低。
2. **你需要断点续跑和人机协同吗？** 如果需要，自己实现状态持久化的成本会超过学习框架的成本——这时候框架是划算的。

**框架最大的价值不在"写起来爽"，而在"状态持久化 + 可观测 + 人工介入"这套生产基建。**
:::

## 主流方案对比

| 方案 | 定位 | 优势 | 代价 | 适合 |
| --- | --- | --- | --- | --- |
| **LangGraph** | 图状编排 | 显式状态图、支持环与分支、持久化强、人机协同好 | 概念多、学习曲线陡 | 复杂业务流程、生产系统 |
| **LangChain** | 组件库 | 生态最大、适配器最全 | 抽象层多、版本变动频繁、调试困难 | 快速原型、组件拼装 |
| **AutoGen** | 多 Agent 对话 | 多角色协作、代码执行沙箱成熟 | 对话式控制流难以预测 | 研究、多 Agent 实验 |
| **CrewAI** | 角色化多 Agent | 心智模型简单、上手快 | 灵活度有限、复杂分支吃力 | 快速搭多角色协作 Demo |
| **Dify / Coze 等** | 低代码平台 | 可视化编排、开箱即用 | 深度定制受限、有平台锁定 | 业务侧自助搭建、轻量场景 |
| **自研** | 完全自主 | 无锁定、极致可控、依赖少 | 全部基建自己写 | 核心业务、有平台团队 |

:::callout warn 关于 LangChain 的版本问题
它的抽象层多、迭代快，早期代码在版本升级后经常跑不起来。**如果要用于生产，建议锁定版本并做依赖隔离。**

一个务实的做法：**用它的组件（模型适配、文档加载、向量库连接），但不要用它的 Agent Executor 承载核心流程。**
:::

## 一个更值得考虑的选择：轻量自研

对于大多数业务场景，一个 300 行左右的编排层就够用了，而且完全可控：

```python {3-16} title="轻量编排层：图 + 状态 + 持久化"
class Node:
    name: str
    run: Callable[[State], State]
    next: Callable[[State], str]      # 返回下一个节点名

class Graph:
    def __init__(self, nodes: dict[str, Node], entry: str, max_steps=30):
        self.nodes, self.entry, self.max_steps = nodes, entry, max_steps

    def run(self, state: State, store: CheckpointStore) -> State:
        name, steps = self.entry, 0
        while name and steps < self.max_steps:
            state = self.nodes[name].run(state)
            store.save(state.run_id, name, state)      # 持久化：支持断点续跑
            name = self.nodes[name].next(state)        # 分支：由函数决定
            steps += 1
        return state
```

:::callout tip 这段代码的价值
它只有 16 行，却覆盖了框架 80% 的核心能力：**节点、分支、循环、步数上限、状态持久化**。

剩下的 20%（流式、并行、可视化、人机协同）可以按需补。**先写这 16 行，等你真的需要更多能力时再考虑引入框架**——那时你也更有能力判断哪个框架合适。
:::

## 选型决策路径

```text title="框架选型决策树"
流程需要人工审批 / 断点续跑吗？
├── 不需要 → 流程有分支或环吗？
│            ├── 没有 → ✅ 直接自研（几十行）
│            └── 有   → 自研图编排，或 LangGraph
└── 需要 → 团队有平台工程能力吗？
          ├── 有 → LangGraph（或自研 + 自建持久化）
          └── 没有 → 低代码平台（Dify 等），接受定制限制

是多 Agent 协作场景吗？
└── 是 → 角色化的用 CrewAI，需要沙箱执行代码的考虑 AutoGen
       （但先回到第 11 章确认：真的需要多 Agent 吗？）
```

## 避免锁定：三条工程纪律

无论选什么框架，这三条纪律能显著降低未来的迁移成本：

1. **提示词与业务逻辑不进框架**。放在自己的 `prompts/` 与业务层，框架只做编排。
2. **工具接口用自己的定义**。用适配器转成框架要求的格式，而不是让框架的类型定义渗透到工具实现里。
3. **状态结构自己定义**。持久化的状态对象是你最核心的资产，不要用框架的私有结构。

```python {2-8} title="适配器模式：隔离框架依赖"
# ✅ 自己的工具定义（不依赖任何框架）
def search_kb(query: str, top_k: int = 3) -> list[dict]: ...

# 仅在编排层做一次适配
def to_framework_tool(fn):
    return adapt(fn)   # 转换逻辑集中在这一处，业务代码不受影响
```

:::callout danger 反面教材
把框架的 `Message`、`AgentState`、`Tool` 类型直接用在业务代码里（包括 API 层、数据库层），会导致**升级框架 = 重写业务**。

这类技术债在半年后会以"我们被框架绑死了"的形式爆发。
:::

## 关于低代码平台

Dify、Coze 这类平台在业务侧自助搭建场景下很有价值，但要清醒认识边界：

| 适合 | 不适合 |
| --- | --- |
| 内部工具、轻量问答、流程明确 | 核心业务链路、高并发、深度定制 |
| 业务人员自助搭建 | 需要精细控制上下文与成本 |
| 快速验证想法 | 需要自定义工具协议与安全策略 |

:::callout warn 成本模型要算清
低代码平台的计费方式（按调用次数、按 token 加价、按坐席）在规模化后可能与自建差出数倍。**上线前一定要按 6 个月后的预期量算一遍总成本**，不要被"免费额度"迷惑。
:::

## 本章要点

- 框架的核心价值是**生产基建**（状态持久化、可观测、人机协同），不是"写起来快"。
- **LangGraph** 适合复杂流程与生产；**LangChain** 更适合组件复用；**AutoGen/CrewAI** 面向多 Agent；**低代码平台** 适合业务自助与轻量场景。
- **很多场景只需要一个 16 行的图编排层**。先自研，需要时再引入框架。
- 三条反锁定纪律：**提示词不进框架、工具接口自定义、状态结构自定义**。
