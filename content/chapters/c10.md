# Agent 系统解剖：五大核心组件

从第 3 部分开始，视角从"机制"上升到"系统"。这一章给出一个可以直接照着搭的架构蓝图。

## 五大组件

:::diagram anatomy caption="图 10-1 · Agent 系统解剖：推理内核 + 四个协作组件"
:::

| 组件 | 职责 | 一句话理解 |
| --- | --- | --- |
| **推理内核** | 理解、决策、生成 | 大脑 |
| **规划器** | 任务分解、顺序编排、重规划 | 前额叶 |
| **记忆** | 状态保存、历史检索、知识持久化 | 海马体 |
| **工具层** | 与外部世界交互 | 手脚 |
| **执行环境** | 调度、沙箱、超时、重试、审计 | 躯干 |

:::callout key 为什么要把"执行环境"单列出来
很多初版实现把执行逻辑写在主循环里，几百行之后就无法维护了。**把执行环境独立出来，能获得三个关键能力：**

1. **统一的安全边界**：所有外部交互都经过同一层校验，不会遗漏。
2. **统一的可观测**：每个动作的耗时、结果、成本在同一处记录。
3. **可替换**：本地执行换成沙箱执行、同步换成异步，不影响主循环。

**它是 Agent 从"脚本"走向"系统"的标志。**
:::

## 各组件接口设计

### 推理内核接口

```python {1-8} title="内核只做三件事"
class Reasoner(Protocol):
    def plan(self, context: Context, tools: list[ToolSpec]) -> Plan: ...
        # 输入上下文与工具，输出结构化决策

    def reflect(self, history: list[Step], goal: str) -> Reflection: ...
        # 判断是否有进展、是否需要改变策略

    def synthesize(self, goal: str, facts: list[Fact]) -> str: ...
        # 把已确认的事实组织成最终回答
```

:::callout tip 内核要"可替换"
把内核抽象成接口的最大好处是：**模型升级、换供应商、A/B 测试不同提示词，都不需要改动其他组件。** 生产系统里这是必需的——模型迭代速度远快于业务代码。
:::

### 记忆接口

```python {1-7} title="统一的记忆接口"
class Memory(Protocol):
    def recall(self, query: str, k: int, scope: Scope) -> list[MemoryItem]: ...
    def write(self, item: MemoryItem) -> str: ...
    def forget(self, item_id: str, reason: str) -> None: ...   # 标记失效，非物理删除
    def summarize(self, task_id: str) -> Summary: ...
```

`scope` 参数不可省略——它是租户/用户/权限隔离的载体。第 7 章强调过：**权限过滤必须发生在检索阶段。**

### 工具层接口

```python {1-6} title="工具描述与执行分离"
class ToolSpec(NamedTuple):
    name: str
    description: str          # 给模型看的
    schema: dict              # JSON Schema，用于校验
    fn: Callable              # 给运行时用的
    side_effect: bool         # 是否有副作用（决定是否需要审批）
    timeout: float
```

`side_effect` 字段很关键：**运行时据此决定是否走审批流程**（第 15 章）。

### 执行环境接口

```python {2-9} title="执行环境承担所有脏活"
class Runtime(Protocol):
    def execute(self, call: ToolCall, ctx: RunContext) -> Observation:
        # 内部完成：schema 校验 → 权限校验 → 限流 → 超时 → 重试
        #          → 幂等保护 → 审计日志 → 错误信息翻译

    def budget(self) -> Budget: ...          # 剩余步数/Token/时间
    def trace(self) -> Trace: ...            # 完整调用链
```

## 目录结构参考

一个可维护的 Agent 工程，通常长这样：

```text title="推荐的项目结构"
agent/
├── core/
│   ├── loop.py           # 主循环（第 5 章）
│   ├── planner.py        # 规划器（第 6 章）
│   ├── reasoner.py       # 推理内核适配层
│   └── state.py          # 会话状态定义
├── memory/
│   ├── working.py        # 上下文组装
│   ├── session.py        # 会话记忆
│   └── longterm.py       # 长期记忆 + 检索
├── tools/
│   ├── registry.py       # 工具注册与描述生成
│   └── impl/             # 具体工具实现
├── runtime/
│   ├── executor.py       # 执行环境
│   ├── guard.py          # 护栏（第 15 章）
│   └── budget.py         # 预算控制
├── prompts/              # 提示词单独版本化
├── eval/                 # 评估集与评测脚本（第 14 章）
└── api/                  # 对外接口层
```

:::callout tip 把 prompts 单独放一个目录
提示词是 Agent 的"业务逻辑"，必须**可版本化、可 diff、可回滚、可 A/B**。

把提示词散落在 Python 字符串里，是后期最难维护的技术债之一。
:::

## 控制流：状态机还是自由循环

这是架构上必须做的一个选择：

| 方式 | 描述 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- | --- |
| **纯自由循环** | 模型完全决定下一步 | 灵活 | 难预测、难审计 | 探索型任务 |
| **状态机编排** | 节点固定，模型只在节点内决策 | 可预测、可审计 | 不够灵活 | 业务流程 |
| **混合**（推荐） | 粗粒度状态机 + 节点内自由循环 | 兼顾 | 实现稍复杂 | 大多数生产场景 |

```python {3-13} title="混合模式：状态机包住自由循环"
GRAPH = {
    "intake":      ["classify"],                 # 状态机定义粗粒度流程
    "classify":    ["retrieve", "answer", "handoff"],
    "retrieve":    ["analyze"],
    "analyze":     ["answer", "retrieve"],       # 允许回退，但有环检测
    "answer":      ["verify"],
    "verify":      ["answer", "handoff"],        # 校验不过可重答
}

def step(state):
    node = state.node
    if node in FREEFORM_NODES:                   # retrieve / analyze 内部用 ReAct
        return run_react_subtask(state, node)    # 自由循环，但有步数上限
    return TRANSITIONS[node](state)              # 其余节点是确定性的
```

:::callout key 混合模式的工程价值
**粗粒度状态机给了你三样东西**：可预测的流程（能画出图）、明确的埋点位置（每个节点都能度量）、以及**天然的环检测**（`analyze → retrieve → analyze` 循环超过 N 次就中止）。

**节点内的自由循环保留了灵活性**：模型仍然可以在"检索"这一步自己决定查什么、查几次、怎么改写关键词。
:::

## 数据流：一次请求的完整旅程

把组件串起来看，一次请求是这样的：

```text title="一次请求的数据流"
用户输入
  → [护栏] 输入校验、注入检测
  → [记忆] 召回相关长期记忆（带权限过滤）
  → [上下文组装] 规则 + 工具 + 记忆 + 目标
  → [规划器] 产出计划或下一步动作
  → [执行环境] 校验 → 执行 → 记录
  → [记忆] 写入新事实
  → [反思] 有进展吗？预算够吗？循环还是终止？
  → ...（循环）
  → [护栏] 输出校验、脱敏
  → 用户输出
  → [审计] 全链路 Trace 落库
```

:::callout info 注意"护栏出现两次"
输入护栏和输出护栏是**两个不同的东西**，都要有：

- **输入护栏**防的是：提示注入、越权意图、超范围请求。
- **输出护栏**防的是：数据泄露（PII）、事实错误、不当内容。

只做其中一个，都会留下明显的缺口。第 15 章详细展开。
:::

## 本章要点

- 五大组件：**推理内核、规划器、记忆、工具层、执行环境**。
- **执行环境必须独立**——它是安全、可观测、可替换性的载体，是 Agent 从脚本走向系统的标志。
- 接口设计要点：内核可替换、记忆带 scope、工具分 `spec`/`fn`、执行环境承担所有防御逻辑。
- **提示词要单独版本化**，它是业务逻辑的一部分。
- 控制流推荐**混合模式**：粗粒度状态机 + 节点内自由循环。
- 护栏要**同时覆盖输入和输出**两侧。
