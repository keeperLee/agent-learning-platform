# 能力边界、幻觉与风险认知

上一章列出了大脑的五个短板。这一章把它们算成一笔具体的账——因为**Agent 的风险不是单点的，而是乘法累积的**。

## 错误累积：一个必须算清的账

假设你的 Agent 平均需要 8 步完成任务，每一步的成功率是 95%（这已经是很乐观的假设）：

```python {3-8} title="错误累积的数学直觉"
steps = 8
step_success = 0.95

overall = step_success ** steps
print(f"整体成功率：{overall:.1%}")   # 66.3%

# 如果把单步提升到 99%
print(f"提升到 99%：{0.99 ** steps:.1%}")   # 92.3%
```

把这张表算全，结论会更刺激：

| 步数 \ 单步成功率 | 90% | 95% | 99% | 99.9% |
| --- | --- | --- | --- | --- |
| 5 步 | 59% | 77% | 95% | 99.5% |
| 10 步 | 35% | 60% | 90% | 99.0% |
| 20 步 | 12% | 36% | 82% | 98.0% |
| 50 步 | 0.5% | 7.7% | 60% | 95.1% |

:::callout key 这张表改变了什么
它解释了为什么 Agent 工程的重心**不是"把单步做到极致"，而是"控制步数 + 加校验 + 允许回滚"**：

- **控制步数**：能用 3 步解决的，不要设计成 10 步。第 6 章的规划、第 9 章的上下文压缩都在做这件事。
- **加校验**：每一步的关键产物做确定性校验，把错误拦在早期。第 15 章的护栏就是干这个。
- **允许回滚**：失败不是灾难，"失败了还能退回来"才是可靠系统的标志。
:::

更麻烦的是：**错误不是独立分布的**。如果第 2 步检索到了错误文档，第 3、4 步会基于这个错误继续推理，最终输出一个"逻辑自洽但事实错误"的答案。这种错误比单点错误更难发现，因为每一步看起来都很合理。

## 六类高频失败模式

下面这张表是排查线上问题的常用清单，建议在做设计评审时逐条对照：

| 失败模式 | 表现 | 根因 | 缓解手段（章节） |
| --- | --- | --- | --- |
| **幻觉** | 编造事实、引用不存在的来源 | 模型概率生成 + 上下文中无依据 | RAG 强制引用（13）、输出校验（15） |
| **跑偏** | 做着做着忘了原始目标 | 上下文被中间结果淹没 | 目标重述、滚动摘要（9） |
| **死循环** | 反复调用同一个工具 | 缺少终止条件 / 无进展检测 | 最大步数、重复检测（5） |
| **工具误用** | 选错工具或传错参数 | 工具描述含糊、参数无 schema | 工具设计规范（8） |
| **权限越界** | 执行了不该执行的操作 | 权限校验缺失 | 最小权限、动作审批（15） |
| **成本失控** | 单次任务消耗几千次调用 | 无预算上限、无提前终止 | Token 预算、熔断（14、20） |

### 跑偏的典型过程

```text title="跑偏是怎么发生的（真实日志片段）"
第 1 步：目标 = 分析 Q3 销售下滑原因 ✓
第 3 步：调用 query_db 查询订单表 ✓
第 5 步：发现有几条异常订单，决定深入调查异常
第 8 步：开始追查异常订单的支付渠道
第 12 步：开始调查支付渠道的对接方
第 16 步：...
```

**目标在第 5 步就被"更有趣的子问题"替换了。** 缓解方法有两个，都很简单但非常有效：

1. **每一轮都把原始目标重新注入**（放在上下文的末尾，利用位置效应）。
2. **设置"偏离检测"**：让 Agent 每 N 步自问一次"我现在的行动和原始目标的关系是什么"，答不上来就强制回到主线。

## 什么时候不该用 Agent

这是本章最重要的一节。Agent 很酷，但它**不应该成为默认选项**。

:::callout danger 五个明确的"不要用 Agent"信号
1. **流程可以完全枚举**。如果所有可能的路径你都能画成流程图，那就写代码，不要交给模型。代码更快、更稳、更便宜。
2. **错误代价不可接受且无法回滚**。比如直接操作生产数据库的写操作、发送对外邮件、执行支付。这类场景要么彻底不用 Agent，要么把 Agent 限制在"准备动作 + 人工确认"的范围内。
3. **对延迟极度敏感**。Agent 的多轮调用天然意味着秒级到分钟级的延迟。要求 200ms 内响应的高频接口不适合。
4. **有确定性的简单解法**。字符串匹配能解决的分类问题，用正则；能用一个 SQL 查出来的，别让模型写 SQL 再执行。
5. **无法建立评估**。如果你没法判断 Agent 做得好不好，那它上线就是在赌博。**没有评估就没有迭代能力。**（第 14 章）
:::

决策时可以这样问自己：

```text title="选型决策路径"
任务路径能否预先枚举？
├── 能 → 写代码（可能用 LLM 做其中的模糊环节）
└── 不能 → 错误代价是否可接受/可回滚？
      ├── 否 → 人工确认 + Agent 辅助（Human-in-the-loop）
      └── 是 → 是否有办法评估效果？
            ├── 否 → 先建评估集，再谈 Agent
            └── 是 → ✅ 适合做 Agent
```

## 风险清单（设计评审用）

把这一节当作上生产前必须过一遍的清单：

- [ ] **终止条件**：最大步数、最大 Token、最长耗时是否都设了硬上限？
- [ ] **无进展检测**：连续 N 步结果相同，是否能自动中止？
- [ ] **工具权限**：每个工具是否遵循最小权限？写操作是否走了审批？
- [ ] **数据边界**：Agent 能访问的数据范围是否明确？是否可能串到别的租户？
- [ ] **输出校验**：关键产物（金额、日期、ID）是否有确定性校验，而不是只看文本通顺度？
- [ ] **降级路径**：模型/工具不可用时，系统是否能降级到固定流程或人工？
- [ ] **可观测**：每一步的输入输出、耗时、成本是否可追溯？（没有这个，线上问题无从排查）
- [ ] **人工兜底**：用户遇到问题时，能否一键转人工？

:::callout info 一个实用的心态
把 Agent 当作**一个聪明但需要监督的实习生**，而不是一个可靠的自动化程序。你不会让实习生第一天就独立操作生产库，你也不会指望他永不犯错——你会给他明确的边界、可查阅的资料、以及一个随时能介入的上级。这套思路就是 Agent 工程的全部精髓。
:::

## 本章要点

- 错误是**乘法累积**的：8 步 95% 成功率 = 66% 整体成功率。所以重点在**控制步数、加校验、可回滚**。
- 六类高频失败模式各有明确的缓解手段，设计评审逐条对照。
- **Agent 不是默认选项**：路径可枚举、错误不可回滚、延迟敏感、有确定性解法、无法评估——命中任一条都该重新考虑。
- 把 Agent 当作"需要监督的实习生"来设计系统。

第 1 部分到这里结束。你现在应该具备了判断"什么该做、什么不该做"的框架。从下一章开始，我们进入第 2 部分，逐层拆解 Agent 得以运转的五个核心机制。
