# LLM 作为 Agent 的大脑

Agent 的"大脑"就是大语言模型。这一章我们只关心一件事：**这个大脑擅长什么、不擅长什么**。因为后面所有的架构设计，本质上都是在"发挥它的长处、屏蔽它的短处"。

## 大脑需要具备的三种能力

Agent 对模型的要求和普通对话场景不同，主要看三项：

### 一、指令遵循能力（Instruction Following）

模型要能严格按提示词里的规则行事——包括输出格式、边界条件、禁止事项。这决定了提示词工程的上限。

指令遵循能力弱的模型有个典型症状：**它会忽略你写的约束**。你在提示词里写了「只输出 JSON，不要任何解释」，它还是会在 JSON 前面加一句「好的，以下是结果：」。

### 二、结构化输出能力（Structured Output）

Agent 的决策必须能被程序解析。所以模型需要稳定地输出可解析的结构：

```json {2-6} title="Agent 期望的决策输出"
{
  "thought": "用户问的是报销标准，我需要先检索知识库",
  "action": {
    "tool": "search_knowledge_base",
    "args": { "query": "差旅报销标准", "top_k": 3 }
  }
}
```

:::callout warn 为什么"让它输出 JSON"经常失败
三个高频原因：① 提示词里没给完整的 schema 示例；② 上下文里混入了让它"自由发挥"的表述；③ 用廉价模型做复杂结构输出。缓解手段：提供完整示例（few-shot）、使用原生 function calling / JSON mode、加输出校验与重试。
:::

### 三、工具调用能力（Tool Use / Function Calling）

这是现代模型的原生能力：模型不直接输出文本，而是输出一个结构化的"工具调用意图"，由运行时去执行。

:::callout key 一个重要的认知转变
**模型并不执行工具，它只输出"我想调用这个工具"的意图。** 真正的执行发生在你的代码里。这个分工极其重要——它意味着**所有安全校验、权限控制、参数检查都必须由你的代码完成**，不能指望模型自觉。第 15 章会详细展开。
:::

## 采样参数如何影响 Agent 行为

这几个旋钮直接影响 Agent 的稳定性，值得单独说：

| 参数 | 对话场景建议 | Agent 场景建议 | 原因 |
| --- | --- | --- | --- |
| `temperature` | 0.7~1.0（更有创意） | **0~0.3**（更确定） | Agent 要的是可复现的决策，不是多样性 |
| `top_p` | 0.9 | 0.9~1.0 | 与 temperature 二选一调整即可 |
| `max_tokens` | 按需 | 预留足够空间 | 截断会导致 JSON 不完整、工具调用丢失 |

:::callout tip 关于可复现性
即使 `temperature=0`，输出也不保证完全确定（浮点累加、批处理、服务端并行都会带来微小差异）。所以不要把"可复现"建立在模型上，而要建立在**日志与回放机制**上——把每一步的输入输出完整记录下来，出问题时能重放。第 14 章会讲怎么做。
:::

## 上下文窗口 = 工作内存

这是理解 Agent 的关键比喻：**上下文窗口就是大脑的工作内存（RAM），它是有限的、昂贵的、并且有访问顺序效应。**

它和计算机内存的类比关系如下：

| 计算机 | Agent | 特点 |
| --- | --- | --- |
| 内存 RAM | 上下文窗口 | 快、贵、容量有限 |
| 硬盘 | 向量库 / 数据库 | 慢、便宜、容量大 |
| 缓存淘汰 | 历史消息摘要压缩 | 有损，需要策略 |
| 总线带宽 | 每次调用的 token 上限 | 决定单次能处理多少信息 |

## 大脑的五个固有短板

这些短板不是当前模型的 bug，而是**架构决定的特性**。所有 Agent 工程手段，本质上都是在弥补它们：

### 1. 无状态

模型本身不记得任何东西。每一次调用都是全新的开始，"记忆"完全靠你把历史消息重新塞进上下文。所谓"多轮对话"，是应用层不断重放历史的结果。

### 2. 无法感知实时信息

模型的参数里没有"今天"的数据。天气、股价、库存、你公司昨天刚改的报销标准——它都不知道。**这是必须依赖工具的硬性理由。**

### 3. 算术与精确操作不可靠

模型做长数字乘法、大文本精确字符计数、复杂日期推算时，错误率显著上升。这不是能力问题，而是它本质上在做"概率性的下一个 token 预测"，而不是符号运算。

:::callout tip 工程习惯
凡是**有唯一正确答案**的操作，都交给工具：
- 算术、统计 → `calculator` / `python_sandbox`
- 精确字符串处理 → 代码
- 日期推算 → 代码
- 事实性查询 → 检索工具

模型的职责是**决定调用什么**，而不是**自己算**。
:::

### 4. 幻觉

它会用极其流畅、极其自信的语气，说出完全错误的内容。更麻烦的是：**幻觉在文本层面是看不出来的**——错误的引用、不存在的 API、编造的论文，格式都完全正确。

幻觉在 Agent 场景下更危险，因为错误会进入下一步的推理，被当作事实使用。

### 5. 长上下文中的"中间遗忘"

即使上下文窗口有 128K，模型对**开头和结尾的信息利用效率明显高于中间部分**。业界称之为 "lost in the middle"。

:::callout warn 实践含义
- 把最重要的约束（安全规则、输出格式）放在**系统提示的开头**；
- 把当前任务的关键信息放在**用户消息的结尾**；
- 不要指望模型记住 50 条消息之前的一个细节。

第 9 章「上下文工程」会给出完整的编排策略。
:::

## 提示词对 Agent 的影响：一个对照

同样的任务，提示词的写法会让成功率差出数倍。看这个对比：

```text title="❌ 模糊的提示词"
你是一个助手，帮我处理用户的问题。
```

```text title="✅ 结构化的提示词"
你是电商客服 Agent。你的职责范围仅限：订单查询、退换货政策、物流状态。

# 工作原则
1. 遇到不确定的事实，必须先调用 search_knowledge_base 查询，禁止凭记忆回答。
2. 涉及退款金额、账户信息时，禁止在对话中直接输出，引导用户到「我的订单」页面。
3. 如果用户情绪激烈或问题超出职责范围，调用 transfer_to_human 转人工。

# 输出要求
先决策是否调用工具；若无需工具，直接给出回答，不超过 3 句话。
```

差别的本质是：**后者把"边界"和"决策依据"显式写出来了**。Agent 的可靠性很大程度来自这种"把隐含期望显式化"的工作。

## 本章要点

- Agent 对模型的三项核心要求：**指令遵循、结构化输出、工具调用**。
- **模型只输出"调用意图"，执行发生在你的代码里**——安全责任在应用层，不在模型。
- 上下文窗口 = 工作内存：有限、昂贵、有顺序效应。
- 五个固有短板：无状态、无实时信息、算术不可靠、幻觉、中间遗忘。**它们是 Agent 架构存在的理由。**

下一章我们把短板算成一笔具体的账，看看它们组合起来会产生什么样的失败模式，以及——**什么情况下你根本不该用 Agent**。
