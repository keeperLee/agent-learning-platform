# 规划与任务分解

规划是 Agent 相对普通 LLM 应用最本质的能力升级——**它把"一步到位"变成了"分步推进"**。这一章讲三种主流范式，以及它们各自适合什么任务。

## 为什么要规划

先看一个不规划会怎样：

```text title="不规划的典型失败"
用户：帮我分析 Q3 销售下滑的原因

Agent（无规划）：
"Q3 销售下滑可能有以下原因：市场竞争加剧、季节性因素、产品问题、
 渠道变化……"（一段通用套话，没有任何数据支撑）
```

问题不在于模型不会分析，而在于**它没有先想清楚"分析需要哪些步骤和哪些数据"**就开口了。

规划要解决三件事：

1. **分解**：把大目标拆成可执行的子任务。
2. **排序**：确定子任务之间的依赖与并行关系。
3. **分配**：决定每个子任务用什么工具。

:::

## 范式一：ReAct（推理与行动交错）

ReAct = **Reason + Act**。核心思想是让模型在每一步都显式地"想一下再做"，然后用行动结果更新下一步的思考。

```text title="ReAct 的思考结构"
Thought:  我需要先知道公司最新的差旅报销标准
Action:   search_knowledge_base(query="出差 报销标准")
Observation: 一线城市住宿 ≤ 500 元/晚，餐补 100 元/天
Thought:  标准拿到了，现在计算 3 人 5 天的上限
Action:   calculator(expr="(500+100)*5*3")
Observation: 9000
Thought:  信息齐了，可以回答
Final:    合计上限 9000 元
```

**特点**：

| 维度 | 表现 |
| --- | --- |
| 适应性 | ★★★★★ 每步都能根据新信息调整 |
| 全局最优性 | ★★☆☆☆ 容易陷入局部最优，可能绕远路 |
| 可预测性 | ★★☆☆☆ 路径运行时才生成，难以预估成本 |
| 适合场景 | 探索型任务：信息不确定、路径需要边走边看 |

:::callout warn ReAct 的隐性成本
每一步都要把完整历史重新喂给模型，所以 **token 消耗随步数近似二次增长**（第 9 章会算这笔账）。步数一多，成本和延迟都会快速恶化。
:::

## 范式二：Plan-and-Execute（先规划，再执行）

先把完整计划生成出来，再逐步执行。执行过程中如果发现计划有问题，才触发**重规划**。

```python {1-9} title="Plan-and-Execute 骨架"
def plan_and_execute(goal):
    plan = llm_plan(goal)                    # 1. 一次性产出完整计划
    results = {}
    for task in topological_order(plan.tasks):
        if not deps_satisfied(task, results):
            continue
        results[task.id] = execute(task, results)   # 2. 按依赖顺序执行
        if task.failed_twice:
            plan = replan(goal, plan, results)      # 3. 失败触发重规划
    return synthesize(goal, results)                # 4. 汇总产出
```

**特点**：

| 维度 | 表现 |
| --- | --- |
| 适应性 | ★★★☆☆ 只在中途失败时重规划 |
| 全局最优性 | ★★★★☆ 能提前看到全貌，可优化任务顺序 |
| 可预测性 | ★★★★☆ 计划可见，成本可预估 |
| 适合场景 | 步骤相对明确、子任务之间有明显依赖的任务 |

:::callout tip 工程上的最大好处
**计划是一份可见的产物。** 它可以被人在执行前审核、被缓存复用（相似任务直接套用）、被并行化调度（无依赖的子任务同时跑）。这些在纯 ReAct 里都做不到。
:::

## 范式三：Tree of Thoughts（搜索式探索）

把推理过程组织成一棵树，在每个节点**生成多个候选思路并打分**，然后选择最有希望的分支继续展开。

```python {2-6} title="ToT 的核心循环"
def tree_of_thoughts(problem, depth=3, width=3):
    frontier = [Node(state=initial_thoughts(problem))]
    for d in range(depth):
        candidates = []
        for node in frontier:
            for t in generate_thoughts(node, k=width):     # 每个节点展开 k 个候选
                if is_valid(t):                            # 剪枝：可行性检查
                    candidates.append(Node(parent=node, thought=t, score=score(t)))
        frontier = top_k(candidates, k=width)              # 只保留最优的 k 个
    return best_path(frontier)
```

**特点**：

| 维度 | 表现 |
| --- | --- |
| 适应性 | ★★★★★ 能回溯、能比较不同方案 |
| 成本 | ★☆☆☆☆ 调用次数 = 广度 × 深度，非常昂贵 |
| 适合场景 | 有明确评价函数、方案空间大的难题（数学推理、复杂规划、代码架构设计） |

:::callout danger 慎用 ToT
它的成本是 ReAct 的数倍到数十倍。**只有当"走错路的代价远大于多次推理的成本"，并且你有一个可靠的打分函数时，ToT 才划算。** 绝大多数业务场景用不上它。
:::

## 三种范式对照

| | ReAct | Plan-and-Execute | Tree of Thoughts |
| --- | --- | --- | --- |
| 决策时机 | 每步都决策 | 开局决策一次 | 每层决策多次 |
| 可并行 | 否 | **是** | 是 |
| 成本 | 中 | 低~中 | 高 |
| 路径可预测 | 否 | **是** | 部分 |
| 支持回溯 | 弱 | 中（重规划） | **强** |
| 典型应用 | 客服、检索问答 | 数据分析、报表生成 | 数学、架构设计 |

:::callout key 实践中的组合
真实系统很少只用一种。常见组合是：

**Plan-and-Execute 做骨架 + ReAct 做每个子任务。**
即先用计划拿到全局结构（可预测、可并行），再让每个子任务内部用 ReAct 自由探索（灵活、能应对局部不确定性）。
:::

## 重规划：比初次规划更重要

初次规划总是错的——这只是个程度问题。关键在**什么时候触发重规划，以及重规划要不要收敛**。

```python {3-12} title="重规划触发条件"
def should_replan(state):
    return (
        state.same_task_failed >= 2          # 同一任务连续失败 → 计划有问题
        or state.unexpected_dependency       # 出现计划外的依赖
        or state.new_info_contradicts_plan   # 新信息与计划前提冲突
        or state.progress_rate < 0.2         # 进展速度远低于预期
    )

MAX_REPLAN = 2   # 必须有上限，否则会陷入"规划-重规划"的死循环
```

:::callout warn 重规划的两个坑
1. **没有上限**。每次重规划都产生新计划，可能永远在"重新开始"，永远走不到终点。必须设 `MAX_REPLAN`。
2. **完全抛弃旧计划**。正确做法是**增量修改**：把已完成部分作为既成事实传给重规划，让它只调整剩余部分。否则已经花掉的成本全部浪费。
:::

## 代码：一个可用的规划提示词

规划的可靠性，八成取决于提示词结构。这是一个经过验证的模板：

```text {3-9} title="规划提示词模板"
你是任务规划器。请把用户目标拆成可执行的子任务。

# 约束
1. 每个子任务必须能由「单个工具调用」或「一次模型生成」完成。
2. 明确标注依赖关系（depends_on）。
3. 子任务数量控制在 3~7 个；超过 7 个说明粒度太细，请合并。
4. 不要规划"验证"或"总结"类步骤，系统会自动处理。
5. 如果目标本身信息不足，只输出一个子任务：向用户澄清。

# 输出格式（严格 JSON）
{"tasks": [{"id": "t1", "name": "...", "tool": "...", "depends_on": [], "input": "..."}]}

# 用户目标
{goal}
```

:::callout tip 三条被验证有效的约束
- **限制数量（3~7 个）**：太少不够分解，太多则模型开始编造无意义步骤。
- **禁止"验证/总结"步骤**：这类步骤模型写不出有效内容，且会挤占预算。
- **信息不足时只输出澄清任务**：这是防止"基于错误假设规划"的最后一道闸门。
:::

## 本章要点

- 规划的三大作用：**分解、排序、分配**。
- **ReAct** 灵活但路径不可预测、成本近二次增长；**Plan-and-Execute** 可预测、可并行、可审核；**ToT** 强但昂贵，只适合有明确评价函数的难题。
- 实践中常见组合：**Plan-and-Execute 做骨架 + ReAct 做子任务**。
- **重规划必须增量、必须有上限**，否则会陷入反复重来的死循环。
