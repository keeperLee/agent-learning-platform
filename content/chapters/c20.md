# 案例五：企业级落地经验

前面四个案例讲的是"技术怎么做"。这一章讲**组织与工程上真正卡住项目的地方**——从 Demo 到生产之间隔着的六道关卡。

:::callout key 一个残酷的统计
大多数 Agent 项目不是死在技术上的，而是死在：

**Demo 很惊艳 → 小范围试用效果打折 → 无法量化收益 → 预算被砍。**

所以这一章的重点不是"怎么做得更强"，而是"**怎么让项目活下来**"。
:::

## 关卡一：场景选择（决定成败的 80%）

选错场景，后面所有努力都会白费。

| 高分场景特征 | 低分场景特征 |
| --- | --- |
| 路径无法预先枚举 | 流程固定（用代码更划算） |
| 有大量非结构化知识 | 信息在结构化数据库里（一个 SQL 解决） |
| 错误可被人工快速发现和纠正 | 错误会造成不可逆损失 |
| 效果可度量 | 好坏全凭感觉 |
| 有人愿意为"效率提升"买单 | 没有明确业务负责人 |

:::callout danger 三个最常见的错误场景选择
1. **"给全体员工做一个万能助手"**。范围过大，无法评估，没有任何单一指标会变好。
2. **"替代某个岗位"**。政治阻力大，且验收标准模糊。
3. **"做一个技术演示"**。没有业务负责人，上线即结束。

**正确做法：从"某个岗位每周花 10 小时做的、路径不固定的重复劳动"切入。** 范围小、收益可量化、负责人明确。
:::

## 关卡二：数据与权限边界

这是企业落地最常见的技术卡点。

```text title="权限边界的三个必须回答的问题"
1. Agent 能访问哪些数据？
   → 必须给出明确清单，而不是"按用户权限"（那样无法审计）

2. 数据在传输和存储中如何隔离？
   → 多租户场景下，向量库/缓存必须有租户维度

3. 审计要求是什么？
   → 谁在什么时间问了什么、Agent 做了什么，能查多久
```

:::callout warn 向量库的权限隔离最容易出错
很多实现把不同部门/租户的文档放进同一个 collection，靠 metadata 过滤。**一旦过滤条件写漏（或某个分支忘了传），就会串数据。**

更稳妥的做法：
- **物理隔离**：按租户/部门分 collection 或分库；
- **双保险**：物理隔离 + metadata 过滤；
- **定期验证**：写自动化测试，断言"A 部门检索不到 B 部门文档"。

**这才是真正的"零信任"——不假设每一处调用都记得传过滤条件。**
:::

## 关卡三：成本控制

成本失控是项目被砍的最直接原因。

```python {2-9} title="四层成本控制"
# 1. 单次请求预算（防止单个用户拖垮系统）
BUDGET_PER_RUN = Budget(max_tokens=80_000, max_steps=15, max_cost=0.8)

# 2. 单用户日累计（防止异常使用）
BUDGET_PER_USER_DAY = 200_000   # tokens

# 3. 全系统小时熔断（故障保护）
BUDGET_GLOBAL_HOUR = 20_000_000

# 4. 降级策略：预算耗尽时不是报错，而是降级
def on_budget_exhausted(ctx):
    return fallback_to_single_call(ctx)     # 退回单轮 RAG，而不是直接失败
```

:::callout tip 三个省钱且不降质的做法
1. **缓存**：相同/相似的查询结果缓存。企业内部问题重复率往往超过 30%。
2. **分级模型**：路由、意图识别、摘要用便宜的小模型；只有最终推理用大模型。**这一项通常能省 40% 以上。**
3. **精简上下文**：第 9 章讲过，光是精简工具定义就能省 20%。

**先做这三件事，再考虑"要不要少用 Agent"。**
:::

## 关卡四：评估与灰度

```text title="灰度发布的四个阶段"
阶段 1（影子模式）：Agent 只出结果不出给用户，人工对比它与现有流程的差异
   ↓ 差异可接受
阶段 2（内部试用）：小范围内部员工使用，收集失败案例
   ↓ 修正后质量达标
阶段 3（灰度 5%~20%）：真实用户，但要有人工兜底通道
   ↓ 指标稳定
阶段 4（全量）：保留快速回滚能力
```

:::callout key 影子模式是被低估的第一步
它能在**零风险**的前提下拿到真实数据，用来构建评估集、发现问题。很多团队跳过这一步直接灰度，结果第一批用户就成了测试用例——而这往往意味着项目的终结。

**影子模式跑两周，能省掉后面两个月的救火。**
:::

## 关卡五：运维与组织

Agent 上线后需要一个明确的"主人"：

| 角色 | 职责 |
| --- | --- |
| **业务负责人** | 定义成功标准、验收效果、决定优先级 |
| **技术负责人** | 系统稳定性、成本、迭代 |
| **内容维护者** | 知识库/提示词的持续更新（**最容易被忽略，也最容易导致效果衰减**） |
| **值班机制** | 线上问题的响应人 |

:::callout danger 没有"内容维护者"是效果衰减的头号原因
Agent 上线三个月后效果变差，最常见的原因不是模型退化，而是：

- 公司政策改了，知识库没更新
- 新业务上线了，工具没跟上
- 用户的实际问法变了，提示词没调整

**Agent 是一个需要持续维护的产品，不是一个交付即完成的软件。** 这一点必须在立项时就明确，并分配人力。
:::

### 日常运维看板

- [ ] 成功率、P95 延迟、日成本趋势
- [ ] 失败案例 Top 10（按频次排序）
- [ ] 转人工率趋势
- [ ] 知识库更新记录与最近一次校验时间
- [ ] 成本预算使用率

## 关卡六：ROI 论证

这是决定项目能否延续的关键。

```text title="ROI 计算模板"
收益侧（年化）：
  节省人力 = 每次任务节省时间 × 月任务量 × 12 × 人力单价
  例：5 分钟/次 × 8000 次/月 × 12 × 0.8 元/分钟 ≈ 384 万元

成本侧（年化）：
  模型调用 + 向量库 + 服务器 + 人力（开发 + 维护）
  例：模型 18 万 + 基建 6 万 + 人力 60 万 ≈ 84 万元

净收益 ≈ 300 万元 · ROI ≈ 3.6×

风险折减：按 60% 达成率计算 → 净收益约 146 万元
```

:::callout warn ROI 论证的三个常见陷阱
1. **只算节省的工时，不算"质量下降带来的返工"**。必须把返工成本算进去。
2. **忽略维护成本**。内容维护、提示词迭代、评估集维护，往往占人力的 30~50%。
3. **用"必须 100% 准确"作为验收标准**。实际上"比人工快 5 倍且准确率 90%，剩余的由人工复核"通常就是巨大的胜利。

**先用保守假设算一遍，能过就说明项目值得做；过不了，早发现比晚发现好。**
:::

## 上线检查清单（汇总）

| 维度 | 检查项 |
| --- | --- |
| **场景** | 有明确业务负责人；成功指标可量化；错误可人工纠正 |
| **权限** | 数据清单明确；租户物理隔离 + 过滤双保险；审计可追溯 |
| **成本** | 四层预算上限；降级策略；缓存与分级模型已启用 |
| **评估** | 四类用例齐备；规则校验可自动跑；有 prompt 版本管理 |
| **灰度** | 走过影子模式；有回滚方案；有人工兜底通道 |
| **运维** | 有内容维护者；有看板与告警；有值班机制 |
| **安全** | 输入/动作/输出三道护栏；高危动作人工审批；红队测试过 |
| **ROI** | 保守假设下可论证；维护成本已计入 |

## 本章要点

- Agent 项目失败多因**场景选择与组织问题**，而非技术。
- **场景选择决定 80% 的成败**：选"路径不固定、可度量、有人负责、错误可纠正"的小切口。
- **权限要在数据层物理隔离**，不能只依赖每次调用都记得传过滤条件。
- **成本四层控制 + 降级策略**；省钱三招：缓存、分级模型、精简上下文。
- **影子模式**是低成本获取真实数据的最佳方式。
- 必须有**内容维护者**——Agent 是持续维护的产品。
- **ROI 要用保守假设算全**，把维护与返工成本计入。
