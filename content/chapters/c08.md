# 工具调用：从 Function Calling 到 MCP

工具是 Agent 的手。**没有工具，Agent 只是一个会说话的模型；有了工具，它才开始改变世界。**

这一章讲四件事：工具调用的机制、工具描述怎么写、错误怎么处理、MCP 解决了什么问题。

## 机制：模型不执行工具

先破除一个常见误解：

:::callout danger 模型从不执行任何工具
模型做的只有一件事：**输出一段结构化的"调用意图"**。真正的执行发生在你的代码里。

```text
模型输出：  {"tool": "get_weather", "args": {"city": "深圳"}}
   ↓
你的代码：  权限校验 → 参数校验 → 真正发起 HTTP 请求 → 拿到结果
   ↓
你的代码：  把结果作为 tool 角色消息塞回上下文
   ↓
模型输出：  "深圳今天多云，26~31°C，建议带伞。"
```

**这个分工意味着：安全性、权限、限流、超时、幂等——全部是你的责任，不能指望模型自觉。**
:::

## 工具描述：决定选得对不对

工具选错的头号原因是**描述写得太烂**。对比一下：

```json title="❌ 模糊的工具描述"
{
  "name": "search",
  "description": "搜索信息",
  "parameters": { "query": { "type": "string" } }
}
```

```json title="✅ 明确的工具描述"
{
  "name": "search_knowledge_base",
  "description": "在企业内部知识库中检索文档片段。适用于查询公司制度、产品文档、历史工单等内部信息。不适用于查询实时数据（如库存、股价），那类需求请使用 query_database。返回按相关性排序的文本片段及文档 ID。",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "检索关键词，建议使用名词短语，例如 '差旅报销标准 住宿上限'。不要写成问句。"
      },
      "top_k": {
        "type": "integer",
        "description": "返回条数，默认 3，最大 10。条数越多噪声越大。",
        "default": 3,
        "minimum": 1,
        "maximum": 10
      }
    },
    "required": ["query"]
  }
}
```

:::callout key 高可靠工具描述的四要素
1. **是什么**：一句话说明能力。
2. **什么时候用 / 什么时候不要用**（最关键，也最常被省略）。写清楚边界能显著减少工具误用。
3. **参数怎么填**：给出格式要求 + 正反例。
4. **返回什么**：让模型知道能期待什么结构。

**工具描述是 Agent 的 API 文档。** 你给同事写文档有多认真，就该给模型写多认真。
:::

:::callout tip 工具数量也会成为问题
工具越多，模型选择越容易出错。经验值：**单次暴露给模型的工具不超过 20 个**。

工具超过 20 个时，常见解法有两种：
- **工具分组 + 路由**：先用一次轻量调用判断该用哪一组，再暴露该组工具。
- **工具检索**：把工具描述也向量化，按当前任务检索出最相关的 5~8 个工具动态注入。
:::

## 参数校验：永不信任模型的输出

参数字段缺失、类型错误、格式不对——这些每天都在发生。校验是必须的：

```python {3-14} title="参数校验（Pydantic 风格）"
class SearchArgs(BaseModel):
    query: str = Field(min_length=2, max_length=200)
    top_k: int = Field(default=3, ge=1, le=10)

def call_search(raw_args: dict) -> str:
    try:
        args = SearchArgs(**raw_args)
    except ValidationError as e:
        # 关键：把校验错误翻译成模型能理解的指令
        return (
            f"参数校验失败：{e.errors()[0]['msg']}。"
            f"你提供的是 {raw_args}。请按 schema 修正后重试。"
        )
    return do_search(args.query, args.top_k)
```

:::callout tip 校验失败时不要重试同样的调用
模型拿到具体的错误说明后，通常能自我修正。但如果连续 2 次校验失败，说明这个工具当前不可用，应**换工具或降级**，而不是死磕。
:::

## 错误处理：错误信息是给模型的教材

这是本章最实用的一节。工具执行失败时，你返回给模型的内容，直接决定了它能不能自我修复：

| 场景 | ❌ 差的返回 | ✅ 好的返回 |
| --- | --- | --- |
| 参数错误 | `Invalid argument` | `'start_date' 必须是 YYYY-MM-DD 格式，你传的是 '2026/7/1'。请修正后重试。` |
| 无权限 | `403 Forbidden` | `当前用户（普通员工）无权查询全公司数据。可改为查询本部门数据，或引导用户申请权限。` |
| 无结果 | `[]` | `未检索到相关文档。建议：① 换用更宽泛的关键词；② 使用 query_faq 工具查询常见问题。` |
| 超时 | `TimeoutError` | `查询超时（超过 10 秒）。建议缩小时间范围，例如先查最近 7 天。` |
| 限流 | `429` | `接口限流，请等待 2 秒后重试；或降低 top_k 以减少请求量。` |

:::callout key 一句话原则
**每一条错误信息里，都要包含"下一步该怎么做"。**

模型不是程序员，它看不懂堆栈；但它非常擅长遵循明确的建议。
:::

## 重试与幂等

```python {3-10} title="带指数退避的重试"
def call_with_retry(tool, args, max_retry=2):
    for attempt in range(max_retry + 1):
        try:
            return tool.run(args)
        except RateLimitError:
            if attempt == max_retry:
                raise
            sleep(1.5 ** attempt)              # 指数退避，避免加重限流
        except TimeoutError:
            if attempt == max_retry:
                raise
            args = shrink_scope(args)          # 缩小范围再试，而不是原样重试
```

:::callout danger 写操作必须幂等
对于「下单」「发邮件」「写数据库」这类副作用工具，重试可能导致**重复执行**。三种防护手段：

1. **幂等键**：调用时带上 `idempotency_key`，服务端对同一 key 只执行一次。
2. **先查后写**：执行前先查询是否已存在相同操作记录。
3. **两阶段**：先生成待确认动作，由人工或二次校验后才真正执行。

**能用只读工具解决的，绝不用写工具。**
:::

## 工具粒度：粗一点还是细一点

这是设计时最纠结的问题。经验规则：

| 粒度 | 例子 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **过细** | `db_connect` / `db_exec_sql` / `db_fetch` / `db_close` | 灵活 | 模型要串 4 步才完成一件事，错误点成倍增加 |
| **合适** | `query_orders(user_id, start, end)` | 一次调用完成一件事 | 需要提前设计好业务语义 |
| **过粗** | `do_everything(task_description)` | 调用简单 | 又是一次自由发挥，失去工具的意义 |

:::callout key 判断标准
**一个工具应该对应"一个业务语义完整的动作"。**

测试方法：如果你需要向模型解释"调用这个工具前必须先调另外两个工具"，说明粒度太细了；如果工具名是 `process_request` 这种万能名字，说明太粗了。
:::

## MCP：工具的标准化接口

前面讲的都是「你自己给自己的 Agent 写工具」。问题是：**每个框架、每个 Agent 都要重新写一遍相同的工具**（查文件、查数据库、调 GitHub……）。

**MCP（Model Context Protocol）** 要解决的就是这个重复劳动。它定义了一套标准协议，把「工具提供方」和「工具使用方」解耦：

:::columns
:::diagram multiAgent caption=""
:::
---

```text title="MCP 的核心抽象"
MCP Server（工具提供方）
  ├── tools      可被调用的函数
  ├── resources  可读取的数据
  └── prompts    可复用的提示模板

MCP Client（Agent 运行时）
  └── 通过标准协议连接任意 Server，
      无需为每个工具写适配代码
```
:::

:::callout info MCP 带来的三个实际好处
1. **一次编写，处处可用**：一个 GitHub MCP Server 可以被任何支持 MCP 的 Agent 直接使用。
2. **部署解耦**：工具可以独立部署、独立升级、独立鉴权，不用和 Agent 一起发版。
3. **生态复用**：出现大量现成的 Server（文件系统、数据库、浏览器、各类 SaaS），大幅缩短从零到可用的时间。

**但要清醒**：MCP 解决的是「接入效率」，不解决「安全与权限」。引入第三方 MCP Server 时，它获得的权限范围仍需要你显式约束——这属于第 15 章的内容。
:::

:::callout tip 想看一个真实的 MCP Server 长什么样
配套项目 **mini-rag** 通过 `mcp_server.py` 把本地知识库的检索能力包装成标准 MCP 工具：任何支持 MCP 的 Agent 都能直接调用它，不需要为这个知识库单独写适配代码。

这正是本节说的「一次编写，处处可用」。对照源码可以看出协议层实际要处理的事情，比想象中少。

:::

## 本章要点

- **模型只输出调用意图，执行发生在你的代码里**——安全、权限、限流、幂等全是应用层的责任。
- 工具描述要写清「是什么 / 何时用 / 何时不用 / 参数怎么填 / 返回什么」；**单次暴露不超过 20 个工具**。
- 参数必须 schema 校验；**错误信息要给"下一步建议"**，这是模型自我修复的关键。
- 重试要**指数退避 + 缩小范围**；**写操作必须幂等**。
- 工具粒度对应「一个业务语义完整的动作」。
- **MCP** 标准化了工具接入，解决效率问题，但不解决安全问题。
