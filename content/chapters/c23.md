# 完整项目：可运行的客服 Agent

前面 21 章给的是原理和片段。这一章交付一个**完整的、能跑起来的**系统 —— 它就是本仓库里的 [`examples/support-agent/`](https://github.com/keeperLee/agent-learning-platform/tree/main/examples/support-agent)。

它**零第三方依赖**（只用 Python 标准库），**没有 API Key 也能完整跑通**。

## 为什么需要它

从「读完 24 章」到「自己做出一个能用的 Agent」，中间隔着一道鸿沟：

| 只读章节 | 加上完整项目 |
| --- | --- |
| 知道主循环长什么样 | 看到它如何与预算、护栏、Trace 咬合 |
| 知道工具要校验参数 | 看到校验失败时错误信息怎么被模型消化 |
| 知道写操作要审批 | 看到审批回调如何插进执行链路 |
| 知道要记 Trace | 看到一条真实调用链长什么样 |

**片段能讲清道理，但只有完整系统才能暴露"模块之间怎么接"这类问题。**

```bash
git clone https://github.com/keeperLee/agent-learning-platform.git
cd agent-learning-platform/examples/support-agent

python run.py --once "订单 ORD-20260828-0417 的蓝牙耳机想退货，还在期限内吗"
python -m unittest discover -s tests -v
```

## 六个关键设计点

### 一、执行环境是唯一的拦截点

所有「脏活」都收在 `runtime.py` 的 `execute()` 里，主循环因此可以保持干净：

```python {3-8} title="agent/runtime.py · 执行链路"
def execute(self, tool_name, args):
    spec = TOOLS.get(tool_name)                 # ① 工具存在吗
    if spec is None: return self._fail(...)     #    错误信息里带上可用工具清单
    problem = self._validate_args(spec, args)   # ② 参数齐全吗、有没有多余字段
    if problem: return self._fail(...)
    verdict = self.guard.check_action(...)      # ③ 权限够吗、要不要人工审批
    if not verdict.allowed and verdict.rule == "require_approval":
        if not (self.approve and self.approve(spec.name, args)):
            return self._fail(..., "[待人工确认] ……未获得人工批准")
    result = spec.fn(self, **args)              # ④ 真正执行
```

**模型给的参数永远不可信，这里是唯一拦截点。** 顺序不能变：存在性 → 参数 → 权限 → 审批 → 执行。

### 二、错误信息是给模型的教材

对比一下这个工具抛错时的写法：

```python {3-5} title="agent/tools.py · 可教学的错误"
if not re.fullmatch(r"(ORD-\d{8}-\d{4}|[A-Za-z]{0,4}\d{4})", key, re.I):
    raise ToolError(
        f"订单号格式不正确：{key!r}。正确格式形如 ORD-20260828-0417，"
        f"或直接提供 4 位尾号（如 0417）。")
```

它没有说 `Invalid argument`，而是**给出了正确格式和一个可照抄的例子**。项目里有 8 处这样的错误信息，测试专门断言了它们「包含正确范围或示例」—— 因为**模型能不能自我修复，取决于错误信息写得够不够具体**。

### 三、权限校验必须在工具内部做

:::callout danger 只靠提示词说「只能查自己的订单」是不够的
```python {4-6} title="agent/tools.py · 归属校验"
order = ctx.store.get_order(key) or ctx.store.find_order_by_suffix(key)
if order["user_id"] != ctx.settings.user_id:
    raise ToolError("该订单不属于当前登录用户，无法查询。"
                    "如果用户认为订单归属有误，建议调用 transfer_to_human 转人工核实。")
```

演示数据里特意放了一条**属于其他用户的订单**（`ORD-20260701-0912`）。测试会断言：查询它一定被拒绝。

生产系统里，这一层还要叠加数据库行级权限或独立受限凭证 —— 提示词永远只是"软约束"。
:::

### 四、写操作默认进审批队列

```python {3-7} title="agent/guard.py · 高危动作识别"
if action == "write" and self.settings.user_role != "admin":
    # 高危动作一律转审批，不让模型自己决定（fail-closed）
    return GuardResult(allowed=False, rule="require_approval",
                       message=f"「{tool}」属于写操作，需要人工确认后才能继续。")
```

审批不是硬编码的弹窗，而是**注入的回调**：

| 场景 | 注入的 `approve` |
| --- | --- |
| 交互式 CLI | 直接问用户 y/N |
| 单元测试 | 固定返回 `True` 或 `False` |
| 生产环境 | 创建审批工单并挂起，等待回调 |

**同一套代码，三种行为。** 这就是"可测性是设计出来的"。

### 五、幂等键让重试是安全的

```python {3-8} title="agent/tools.py · 幂等保护"
key = f"{ctx.settings.user_id}:{order['order_id']}:{ctx.settings.today}"
existing = ctx.store.has_refund_request(key)
if existing:
    return {"status": "already_submitted", "request_id": existing["request_id"],
            "note": "同一订单当天已提交过退款申请，本次未重复创建。"}
```

实际验证一下（跨进程仍然生效）：

```text title="连续执行两次同一笔退款申请"
第 1 次 → {"status": "submitted", "request_id": "RF20260920001", "amount": 299.0}
第 2 次 → {"status": "already_submitted", "request_id": "RF20260920001",
           "note": "同一订单当天已提交过退款申请，本次未重复创建。"}
```

### 六、Mock 与真模型无缝切换

```python {1-3} title="agent/config.py · 一行切换"
@property
def use_mock(self) -> bool:
    return not self.api_key          # 没有 Key 就用离线 Mock
```

:::callout info 关于 MockLLM 的诚实说明
`MockLLM` 是一个**规则实现的模拟器**，用关键词和消息历史模拟"模型大概会怎么决策"。

它**不是真实模型**，不具备泛化能力 —— 换个问法就可能失灵。它的价值是让你在不花钱、不联网的前提下观察完整的循环、工具调用、护栏与 Trace。

**用 Mock 测流程，用真模型测效果** —— 这两件事的职责不同，成本差好几个数量级（[第 14 章](#/chapter/c14)）。
:::

## 一次完整运行的轨迹

```text
你 > 订单 ORD-20260828-0417 的蓝牙耳机想退货，还在期限内吗

[第 1 轮] 思考：先确认订单状态，再决定查物流还是政策
         行动：get_order({"order_id": "ORD-20260828-0417"})
         观察：{"status": "已签收", "signed_at": "2026-08-30", "amount": 299.0, ...}

[第 2 轮] 思考：结合订单信息核对相关政策
         行动：search_knowledge_base({"query": "退货 期限 质量", "top_k": 3})
         观察：命中 KB-RETURN-001（7 天）、KB-RETURN-003（质量问题 15 天）

[第 3 轮] 思考：计算签收至今的天数，判断是否还在期限内
         行动：calculator({"expr": "days_between('2026-08-30', '2026-09-20')"})
         观察：{"result": 21, "unit": "天"}

[第 4 轮] 判断：信息已足够，准备输出

客服 > 订单 ORD-20260828-0417（蓝牙耳机 Pro，299.0 元）当前状态为「已签收」，
       签收于 2026-08-30。签收至今已 21 天。相关政策：商品签收后 7 天内
       [KB-RETURN-001]；质量问题不受 7 天限制，可在 15 天内申请 [KB-RETURN-003]。

本次任务：3 次工具调用 · 4 次模型调用 · 约 5,769 tokens · $0.0009
```

注意三个细节，它们都是前面章节的落地：

1. **数字交给工具算**（`days_between` 而不是心算）—— [第 3 章](#/chapter/c03)
2. **每次引用都带编号** `[KB-RETURN-001]` —— [第 13 章](#/chapter/c13)
3. **目标每一轮都重新注入**（放在上下文末尾）—— [第 9 章](#/chapter/c09)

## 测试：33 项，零成本

```bash
python -m unittest discover -s tests -v
# Ran 33 tests in 0.037s — OK
```

覆盖的不是"回答好不好"，而是**工程正确性**：

| 分组 | 断言示例 |
| --- | --- |
| 知识库 | 块内容含标题路径；**失效版本绝不能被召回** |
| 工具 | 未知工具列出可用清单；缺参数/多参数被拒；**不归属自己的订单被拒** |
| 护栏 | 注入被拦；批量导出被拦；写操作默认需审批；PII 脱敏正确 |
| 主循环 | **护栏生效时模型调用次数为 0**；卡死的 Agent 被中止；天数计算必须调工具 |
| 幂等 | 同一订单重复申请只产生一条工单 |
| Trace | 落盘且含 `prompt_hash`、`cost_usd`、`steps` |
| 解析容错 | JSON 被代码块包裹、夹杂解释文字时仍能解析 |

:::callout tip 这套测试写出来时抓到了 4 个真实 bug
- PII 正则引用了不存在的捕获组，脱敏直接抛异常
- 注入检测的正则写得太死，"忽略**之前所有**指令"这种常见句式匹配不上
- 知识库元数据解析要求"元数据必须紧跟标题"，中间有个空行就失效
- Mock 的订单分支被一个多余的前置判断短路，导致订单类问题全走到政策分支

**全是看代码看不出来的问题。** 这也是[第 14 章](#/chapter/c14)强调「先建评估/测试」的原因。
:::

## 刻意保留的简化

| 简化点 | 生产环境应该怎么做 |
| --- | --- |
| 检索用字符 bigram 打分 | 换成嵌入模型 + 向量库，并做混合检索与重排（[第 13 章](#/chapter/c13)） |
| Trace 落本地 JSON | 接入 OpenTelemetry / Langfuse 等平台 |
| 长期记忆存本地 JSON | 用数据库，并做好租户隔离 |
| 护栏用正则匹配注入特征 | 正则只能挡低级攻击，真实防护靠权限收敛 + 动作审批（[第 15 章](#/chapter/c15)） |
| 每一轮提问是独立任务 | 真实客服需要多轮会话，复用同一个 `SessionMemory` |

**它们被简化的是"实现"，不是"结构"。**

## 本章要点

- 片段讲清道理，**完整系统才暴露"模块之间怎么接"**。
- 模块划分、接口边界、护栏位置、Trace 字段 —— 这些**跨项目通用**，可以直接照搬。
- 执行环境是**唯一的拦截点**，顺序固定：存在性 → 参数 → 权限 → 审批 → 执行。
- **错误信息是给模型的教材**：给出正确格式和可照抄的例子，模型才能自我修复。
- **权限校验必须在工具内部做**；写操作默认进审批队列，审批通过回调注入以保持可测。
- **幂等键让重试安全**；Mock 与真模型一行切换，各自职责不同。
- 33 项零成本测试抓出了 4 个看代码发现不了的 bug —— **先建测试，再谈优化**。
