# RAG 与知识库架构

Agent 的"知识"从哪来？两条路：训练进参数里，或者**运行时检索出来**。前者昂贵且滞后，后者就是 RAG。

这一章讲清楚 RAG 的完整链路，以及在 Agent 场景下 RAG 需要做的三处关键改造。

## 完整链路

:::diagram rag caption="图 13-1 · RAG 链路：离线构建知识库 + 在线检索增强"
:::

拆开看是六个环节，每个环节都有典型的失效点：

| 环节 | 做什么 | 典型失效 |
| --- | --- | --- |
| 切分 | 把长文档切成可检索的块 | 切在句子中间，语义被截断 |
| 向量化 | 把文本转向量 | 用了不适合中文/领域的嵌入模型 |
| 检索 | 相似度召回 Top-K | 召回不到，或召回一堆相似但无用的 |
| 重排 | 对召回结果精排 | 跳过重排，噪声进入上下文 |
| 组装 | 拼进提示词 | 塞太多，挤掉其他信息 |
| 生成 | 基于证据作答 | 不做引用约束，模型自由发挥 |

:::callout key 一个残酷的经验
**RAG 的效果上限由"检索质量"决定，而不是由"生成模型"决定。**

如果检索没找到正确的文档，再强的模型也只能编。所以调优顺序应该是：**切分 → 嵌入模型 → 重排 → 提示词**，而不是反过来。
:::

## 环节一：切分策略

切分是最容易被忽视、也最影响效果的一步。

| 策略 | 做法 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- | --- |
| 固定长度 | 每 N 字符切一块 | 简单 | 常切断语义 | 无结构文本 |
| 按结构 | 按标题/段落/表格切 | 语义完整 | 依赖文档结构 | Markdown、制度文档 |
| 递归切分 | 先按段，超长再按句 | 平衡 | 实现稍复杂 | 通用（推荐默认） |
| 语义切分 | 相邻句子相似度骤降处切 | 语义最优 | 成本高、慢 | 高质量要求场景 |

```python {2-6} title="带重叠的递归切分"
def chunk_document(doc, size=600, overlap=100):
    # 先按结构切，超长再按句子切，最后兜底按长度切
    blocks = split_by_headings(doc)                  # 保留标题层级信息
    chunks = []
    for b in blocks:
        for piece in recursive_split(b.text, size=size):
            # 把标题信息带上，检索时能作为上下文
            chunks.append(f"【{b.heading_path}】\n{piece}")
    # 相邻块保留重叠，避免答案正好在边界上被切断
    return add_overlap(chunks, overlap)
```

:::callout tip 三个高性价比的切分细节
1. **把标题路径拼进块内容**。`【第 3 章 > 报销标准 > 住宿】` 这类前缀能显著提升召回准确率，因为检索时有更多上下文。
2. **保留 10~20% 重叠**。答案落在切分边界上是很常见的失败原因。
3. **表格不要按行切**。表格按行切会丢失表头，导致语义完全错乱——整个表格作为一个块，或者把表头复制到每一行。
:::

## 环节二与三：检索与重排

**纯向量检索不够用**，生产环境通常是混合检索：

```python {2-11} title="混合检索 + 重排"
def retrieve(query: str, k: int = 5):
    # 1. 向量检索：擅长语义相似
    vec_hits = vector_search(query, top_k=20)
    # 2. 关键词检索：擅长精确匹配（型号、ID、专有名词）
    kw_hits = bm25_search(query, top_k=20)
    # 3. 融合（RRF 倒数排名融合，不需要调权重）
    fused = reciprocal_rank_fusion(vec_hits, kw_hits)
    # 4. 重排：交叉编码器对 query-doc 对做精排，比向量精确得多
    reranked = cross_encoder_rerank(query, fused[:20])
    # 5. 过滤：权限、时效、版本（必须在生成前完成）
    return filter_valid(reranked)[:k]
```

:::callout warn 为什么必须做重排
向量检索是"双塔"结构——查询和文档分别编码后算相似度，速度快但精度有限。**重排模型把查询和文档放在一起编码（交叉编码器），精度高得多，但慢，所以只对 Top-20 做。**

实测中，加一步重排通常能把"正确文档进入 Top-5"的比例提升 15~30 个百分点。这是 RAG 优化里投入产出比最高的一步。
:::

注意演示的第 ③ 步：**重排不只是排序，它还能过滤掉废弃版本**。这一点在制度、政策、API 文档这类会频繁改版的场景里至关重要——**召回了两年前的旧版本，比召回不到更危险。**

## Agent 场景下 RAG 的三处改造

把 RAG 从"问答系统"搬进 Agent，需要做三个改造：

### 改造一：把"检索"变成工具，而不是固定步骤

第 2 章讲过，固定流程的 RAG 是 L3。在 Agent 里，检索应该是一个**可以被多次调用、可以改参数、可以换工具**的动作：

```python {1-8} title="检索作为工具的三种形态"
tools = [
    search_knowledge_base,     # 语义检索：找概念性内容
    query_database,            # 结构化查询：找精确数据
    read_document,             # 按 ID 读取全文：深入阅读某一篇
    list_documents,            # 列出相关文档：先看有哪些再决定读哪个
]
# Agent 可以：先 list 缩小范围 → 再 search 定位 → 再 read 补充细节
```

:::callout key 这个改造带来的能力提升
固定 RAG 只有一次检索机会。Agent 化之后，模型可以：**写不好关键词就改写重试**、**发现召回的文档不够就换个工具**、**读到摘要后按需拉取全文细节**。

这是"检索型问答"和"研究型 Agent"的本质差别。
:::

### 改造二：引用可溯源

Agent 的输出必须能追溯到具体来源。这不只是为了可信，更是为了让**校验成为可能**：

```python {3-9} title="强制引用格式"
# 上下文中的证据带编号
[1] 【差旅办法 v3.2 > 第4章 住宿标准】一线城市住宿上限 500 元/人/晚
[2] 【FAQ > 住宿超标】超出部分需部门 VP 审批，差额自付

# 提示词中的硬约束
"每条事实性陈述必须标注来源编号，格式为 [n]。
 如果证据中没有依据，必须明确说明『资料中未涵盖』，禁止推测。"

# 输出
"一线城市住宿上限为 500 元/人/晚 [1]；超标部分需 VP 审批后自付差额 [2]。"
```

有了引用编号，就可以做**自动化校验**：解析输出中的 `[n]`，检查对应的文档确实存在且确实包含该结论。第 14 章的评估会用到这个机制。

### 改造三：多跳检索

复杂问题需要多步检索，后一步依赖前一步的结果：

```text title="多跳检索示例"
问题：我们公司和 A 供应商的合同里，违约金条款是怎么约定的？

第 1 跳：list_documents(query="A 供应商 合同")     → 找到 3 个候选
第 2 跳：read_document(id="CT-2026-011", section="目录")  → 定位到第 7 章
第 3 跳：read_document(id="CT-2026-011", section="7")     → 拿到违约金条款
第 4 跳：query_database(sql="查 A 供应商历史违约记录")     → 交叉验证
```

:::callout tip 多跳检索的控制要点
- **限制跳数**（一般 3~5 跳），否则容易无限检索；
- **每一跳都要判断"信息够了吗"**，够了就停；
- **记录已经读过的文档 ID**，避免重复读取（这是很常见的浪费）。
:::

## 评估 RAG

RAG 的评估要分开看两个环节，否则无法定位问题：

| 指标 | 衡量什么 | 怎么测 |
| --- | --- | --- |
| **召回率 Recall@K** | 正确文档是否在 Top-K 里 | 标注集：每个问题标出正确文档 ID |
| **精确率 Precision@K** | Top-K 里有多少是相关的 | 同上 |
| **忠实度 Faithfulness** | 回答是否完全基于召回内容 | LLM 裁判 + 人工抽检 |
| **答案相关性** | 回答是否切题 | LLM 裁判 |
| **引用准确率** | 引用编号是否真的支撑结论 | 自动化校验 `[n]` ⭢ 文档内容 |

:::callout danger 最常见的错误：只看最终答案
"答案看起来挺好"是危险的自信来源。因为最终答案可能是模型**用参数里的知识**答出来的，而不是从你检索到的文档里答出来的——这种情况下，一旦用户问到冷门内容，效果会突然崩塌。

**必须单独测召回率。** 召回率不达标，其他优化都是徒劳。
:::

## 本章要点

- RAG 六个环节：**切分、向量化、检索、重排、组装、生成**；效果上限由**检索质量**决定。
- 切分的三个细节：拼入标题路径、保留重叠、表格整块处理。
- 检索要**混合（向量 + 关键词）+ 重排**；重排是投入产出比最高的优化。
- Agent 场景的三处改造：**检索工具化、引用可溯源、多跳检索**。
- 评估必须**单独测召回率**，不能只看最终答案。
