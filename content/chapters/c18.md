# 案例三：数据分析 Agent

数据分析 Agent 的难点和代码助手正好相反：**它没有客观的成功判据**。SQL 能跑通不代表结果正确，"看起来合理"的数字可能是完全错的。

这一章讲如何在这种"无法自动验证"的场景里建立足够的可靠性。

## 可靠性从哪来

三个层次，缺一不可：

| 层次 | 手段 | 拦截的问题 |
| --- | --- | --- |
| **事前** | Schema 注入、业务口径说明 | 用错表/字段、口径理解错 |
| **事中** | 只读校验、成本预估、沙箱执行 | 危险 SQL、全表扫描拖垮库 |
| **事后** | 结果合理性校验、交叉验证 | 数据没错但结论错 |

:::callout danger 最危险的错误：数字是对的，解读是错的
```text
Agent 输出：Q3 销售额环比下降 12.3%，主要原因是华东区下滑。

问题：环比下降 12.3% 是因为去年 Q3 有一次性大促。
      如果看同比，实际是增长 8%。
      Agent 用了"环比"这个口径，得出了相反的结论。
```

**数字没有算错，但用户会被误导。** 这类错误无法靠 SQL 校验发现，只能靠"强制说明口径 + 多口径对比"来缓解。
:::

## 事前：Schema 注入与口径说明

不要把整个数据库的 Schema 塞进去——那会占满上下文且增加选错表的风险。要**按需注入 + 附带业务语义**：

```text {1-14} title="Schema 注入示例"
【可用表】analytics_readonly 库（只读）

表：orders（订单表，一行一单）
  order_id     BIGINT      主键
  user_id      BIGINT      用户 ID
  gmv          DECIMAL     订单金额（含税，未扣退款）★ 计算净收入请用 net_revenue
  net_revenue  DECIMAL     净收入（已扣退款与优惠）★ 财务口径以此为准
  status       VARCHAR     paid / refunded / cancelled ★ 统计销售额必须过滤 status='paid'
  region       VARCHAR     大区：华东/华北/华南/西南 ★ 注意不是"省份"，省份需 join dim_region
  created_at   DATETIME    UTC 时间 ★ 报表口径为北京时间，需 +8 小时

【业务口径】
- "销售额"默认指 net_revenue 且 status='paid'，排除测试账号 (user_id < 1000)
- 行业默认使用同比（YoY）；如需环比必须在结论中明确说明
- 华东区包含上海、江苏、浙江、安徽
```

:::callout key schema 注入的四个必备要素
1. **字段含义与单位**（含税否、时区、币种）
2. **口径规则**（默认用哪个字段、必须过滤什么）
3. **易混淆项的显式提示**（"region 不是省份"）
4. **业务术语到字段的映射**（"销售额" → `net_revenue`）

**这份说明的质量，直接决定了分析结果的正确率。** 它比任何提示词技巧都重要。
:::

## 事中：只有一个 SQL 工具

```python {3-16} title="受约束的 SQL 执行工具"
def run_sql(sql: str, ctx: RunContext) -> str:
    # 1. 只读校验（不要只靠正则，最好用 SQL 解析器）
    if not is_select_only(sql):
        return error("只允许 SELECT 查询。如需其他操作请联系数据团队。")

    # 2. 必须带 LIMIT（防止意外拉取千万行）
    if not has_limit(sql):
        return error("查询必须包含 LIMIT 子句，建议 LIMIT 1000 以内。")

    # 3. 成本预估：解析执行计划，超阈值直接拒绝
    plan = explain(sql)
    if plan.estimated_rows > 5_000_000:
        return error(f"预估扫描 {plan.estimated_rows} 行，成本过高。"
                     f"建议：① 增加时间范围过滤；② 先按天聚合再计算。")

    # 4. 强制时间范围（大表必须）
    if touches_large_table(sql) and not has_time_filter(sql):
        return error("查询大表必须指定时间范围，例如 created_at >= '2026-07-01'。")

    # 5. 超时 + 行数截断
    return execute(sql, timeout=30, max_rows=10_000, conn=ctx.readonly_conn)
```

:::callout warn 为什么强调"用 SQL 解析器而不是正则"
正则很容易被绕过：注释、大小写、多语句、`UNION` 嵌套……**用真正的 SQL 解析器（如 `sqlglot`）做 AST 校验**，同时用**只读数据库账号**做最后一道保险。

两道防线都要有：解析器防"意图"，只读账号防"意外"。
:::

## 事后：结果合理性校验

这是数据分析 Agent 最需要补的一环。三类校验：

```python {2-12} title="结果校验"
def validate_result(result, context) -> list[str]:
    warnings = []
    # 1. 量级校验：与历史同期对比，偏差过大要提示
    if result.metric == "gmv":
        expected = context.history_avg("gmv", same_period=True)
        if abs(result.value - expected) / expected > 3:
            warnings.append(f"当前结果 {result.value} 与历史均值 {expected} 相差超过 3 倍，请核对口径。")

    # 2. 一致性校验：明细求和是否等于汇总
    if has_detail_breakdown(result):
        if abs(sum(result.breakdown) - result.total) > 0.01:
            warnings.append("明细合计与总计不一致，可能存在维度丢失。")

    # 3. 空值/异常校验
    if result.rows == 0:
        warnings.append("查询返回 0 行。请确认时间范围与过滤条件是否正确。")
    if result.has_null_rate > 0.3:
        warnings.append(f"结果中 {result.has_null_rate:.0%} 为空值，可能字段选取有误。")
    return warnings
```

:::callout tip 把警告显示给用户
这些校验结果不要静默丢弃，而是**附在回答后面**：

```text
Q3 净收入为 2,864 万元，环比下降 12.3%（按 net_revenue，status='paid'）。

⚠️ 数据提示：该结果与去年同期相比增长 8.1%，环比下降主要受
   2025 Q3 一次性大促的高基数影响。建议同时参考同比数据。
```

**主动暴露不确定性，比给出一个自信的错答案好得多。**
:::

## 多口径对比：对抗"选择性呈现"

```python {2-8} title="关键指标默认多口径"
def analyze_metric(name: str, period: str):
    return {
        "同比 YoY":  query(f"{name} 同比", period, offset="-12m"),
        "环比 QoQ":  query(f"{name} 环比", period, offset="-3m"),
        "绝对值":    query(f"{name} 本期", period),
        "明细拆分":  query(f"{name} 按大区", period),
    }
```

:::callout key 为什么这很重要
单一口径的结论极易误导。**强制同时给出同比与环比**，能让"高基数导致的环比下滑"这类常见误读自动暴露出来。

这本质上是在用工程手段弥补"模型无法自动判断结论是否正确"的缺陷。
:::

## 沙箱与图表

```python {2-9} title="代码沙箱的用途被低估了"
# 比"让模型算"可靠得多的做法：让模型写代码，让代码算
tools = [
    run_sql(sql),                             # 取数
    run_python(code, timeout=20),             # 计算（pandas 做统计、透视、同比）
    render_chart(df_id, chart_type, mapping),  # 出图（返回图片 URL）
]

# 模型的工作：把"计算意图"翻译成代码
# 代码的工作：做真正的计算
```

:::callout info "让模型写代码"是通用模式
第 3 章说过模型算术不可靠。在数据分析场景里，这个原则的落地方式就是：**模型只负责表达"要算什么"，实际计算全部交给 pandas / SQL。**

同样的思路也适用于：文本统计、日期推算、正则匹配、数据格式转换。
:::

## 交付形态

数据分析 Agent 的产出通常不是一段文字，而是一个**可交互的分析结果**：

| 交付物 | 内容 |
| --- | --- |
| 结论摘要 | 3~5 条要点，结论前置 |
| 数据表 | 可下钻、可排序 |
| 图表 | 趋势图 + 结构图 |
| 口径说明 | 用了哪些表、什么过滤条件、什么口径 |
| SQL 与代码 | 可复现（**关键：让用户能自己验证**） |
| 数据提示 | 上面提到的各类警告 |

:::callout tip "可复现"是数据分析 Agent 的信任基础
把生成 SQL 和 Python 代码一并展示出来，用户可以自己核对逻辑。这比任何"我很确定"的措辞都有说服力。

**在无法自动验证正确性的场景里，透明性就是可靠性。**
:::

## 效果指标

| 指标 | 目标 |
| --- | --- |
| SQL 执行成功率 | ≥ 95% |
| 口径正确率（抽检） | ≥ 95% |
| 多轮修 SQL 的比例 | ≤ 30% |
| 用户追问率 | ≤ 25% |
| 端到端 P95 延迟 | ≤ 20 秒 |

## 本章要点

- 数据分析 Agent 的难点是**没有客观成功判据**，可靠性要靠三层保障：**事前（Schema + 口径）、事中（只读 + 成本控制）、事后（合理性校验）**。
- **Schema 注入要带业务语义**：单位、时区、口径、易混淆项提示——这比提示词技巧重要得多。
- SQL 工具要做**只读校验、强制 LIMIT、成本预估、强制时间范围**；用 SQL 解析器而非正则，并叠加只读账号双保险。
- 事后校验三类：**量级、一致性、空值**；结果要**主动暴露不确定性**。
- **强制多口径对比**（同比 + 环比）对抗选择性呈现。
- 计算交给 **pandas/SQL**，模型只负责表达意图。
- **透明性就是可靠性**：展示 SQL 与代码，让用户可复现。
