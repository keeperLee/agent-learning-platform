## 四、评测基准

做效果评估时，优先复用公开基准，而不是从零造评测集。

| 基准 | 测什么 | 备注 |
| --- | --- | --- |
| [SWE-bench](https://github.com/SWE-bench/SWE-bench) | 真实 GitHub Issue 修复 | 代码 Agent 的事实标准 |
| [GAIA](https://huggingface.co/datasets/gaia-benchmark/GAIA) | 通用助理任务（多跳检索 + 工具） | 人类约 92%，早期模型不到 15% |
| [WebArena](https://webarena.dev/) | 网页操作 | 端到端浏览器任务 |
| [AgentBench](https://github.com/THUDM/AgentBench) | 多环境综合能力 | 8 类交互环境 |
| [τ-bench](https://github.com/sierra-research/tau-bench) | 多轮工具调用 + 规则遵循 | 强调"规则一致性"而非单轮正确 |
| [Terminal-Bench](https://github.com/laude-institute/terminal-bench) | 终端任务 | 偏系统运维与命令行 |

:::callout warn 看基准结果要留意三件事
1. **成本与延迟**：只看准确率不看花费，会得出误导性结论（[AI Agents That Matter](https://arxiv.org/abs/2407.01502) 的核心批评）。
2. **是否泄漏**：部分基准的任务出现在训练数据里。
3. **与你的场景差多远**：公开基准测的能力，可能和你的业务需求几乎无关。**自建 30~50 条真实用例，往往比刷榜更有价值**（[第 14 章](#/chapter/c14)）。
:::

## 六、怎么跟进这个领域

这个领域的信息噪音远大于信号。三条实践建议：

:::callout key 一、按"机制"而非"产品"分类
看到任何新东西，先问：**它接管的是哪一部分控制权？**（[第 2 章](#/chapter/c02) 的分级框架）

- 如果它只是让"单步更强"，价值有限且会被模型升级吞掉；
- 如果它解决的是**状态管理、评估、安全**这类工程问题，价值更持久。

过去两年的历史反复验证了这一点：做"提示词技巧"的项目大量消失，做"可观测/评估/编排基建"的项目活了下来。
:::

:::callout key 二、用"最小复现"代替"收藏"
看到一个声称有效的方法，**用你自己的 30 条评估集跑一遍**。

多数情况下你会发现：效果提升没有宣传的那么大，或者在你的场景下根本不成立。这比读十篇解读文章都有用——而且你会得到一份属于自己的评估集（[第 14 章](#/chapter/c14)）。
:::

:::callout key 三、盯住三个信号源
| 信号源 | 看什么 |
| --- | --- |
| **一手工程博客** | Anthropic / OpenAI / Google 的工程博客，通常比论文更贴近落地 |
| **开源项目的 Issue 与讨论** | 真正的难点都在那里，不在 README 里 |
| **公开基准的榜单变化** | 注意成本与延迟，不只看分数 |

**避开**：只讲"震撼效果"不给失败案例的内容；只演示一次成功、不谈成本与评估的内容。
:::

## 本章要点

- 阅读顺序：**工程指南 → 一手论文 → 开源实现 → 框架文档**。先理解原理，再选工具。
- 必读三篇：**ReAct**（主循环）、**Lost in the Middle**（上下文）、**AI Agents That Matter**（为什么多数宣称不可信）。
- 读开源项目时，重点看**状态管理、重试策略、上下文压缩**这三处，不要只看功能列表。
- 做评估优先复用公开基准，但**自建 30~50 条真实用例的价值更高**。
- 跟进领域的方法：**按机制分类、做最小复现、盯一手信号源**。
