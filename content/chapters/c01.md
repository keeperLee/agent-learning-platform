# 什么是 AI Agent

如果你只记住一句话：**Agent 是一个能自己决定「下一步做什么」、并且真的能动手去做的 AI 系统。**

这句话里有两个关键动词——「决定」和「动手」。少了任何一个，它就不是 Agent。

## 一个可操作的三条判据

市面上的产品几乎都自称 Agent，但用下面三条判据一过，绝大多数会被筛掉：

| 判据 | 含义 | 反例 |
| --- | --- | --- |
| **自主决策** | 下一步做什么由模型自己判断，而不是由代码写死的流程决定 | 固定流程的问答机器人：先检索、再拼提示词、再生成。流程写死在代码里，模型只负责最后一步措辞 |
| **工具行动** | 能调用外部工具改变世界或获取新信息，而不仅是输出文本 | 纯文本生成的写作助手：它只能"说"，不能"做" |
| **闭环反馈** | 会检查行动结果，并据此调整后续行为 | 单次调用的分类/抽取任务：一次进出，没有反馈回路 |

三条都满足，才称得上 Agent。只满足第一条和第二条的，更准确的叫法是 **工具调用型助手**；三条都不满足的，就是普通的 LLM 应用。

:::callout key 一句话区分
**LLM 应用**是「你写好流程，模型填空」；**Agent** 是「你给出目标，模型自己找路径」。判断标准是：**控制流在谁手里**。
:::

## 最小定义

从工程视角，Agent 可以被形式化为一个循环：

```text
状态 S₀ = { 目标, 初始上下文, 可用工具 }
循环 k = 0, 1, 2, ...
  动作 aₖ = LLM(提示(目标, Sₖ, 可用工具))     ← 决策
  观察 oₖ = 执行(aₖ)                          ← 行动 + 反馈
  Sₖ₊₁   = 更新(Sₖ, aₖ, oₖ)                  ← 状态推进
直到 终止条件(Sₖ) 满足
```

看起来简单得可疑。但工程实践中，90% 的难度都藏在三个地方：

1. **`LLM(提示(...))`** —— 怎么让模型稳定地做出正确决策（第 2 部分「核心原理」）；
2. **`执行(aₖ)`** —— 怎么安全、可靠、可观测地执行动作（第 3 部分「架构设计」）；
3. **`终止条件`** —— 怎么让它在该停的时候停（第 3 部分 + 第 4 部分「实战」）。

```text {3,4,6} title="Agent 核心循环 · 三个难点"
状态 S₀ = { 目标, 初始上下文, 可用工具 }
循环 k = 0, 1, 2, ...
  动作 aₖ = LLM(提示(目标, Sₖ, 可用工具))     ← 决策
  观察 oₖ = 执行(aₖ)                          ← 行动 + 反馈
  Sₖ₊₁   = 更新(Sₖ, aₖ, oₖ)                  ← 状态推进
直到 终止条件(Sₖ) 满足
```

注意演示中的几个细节，它们都是工程实践里踩过坑才总结出来的：

- **它没有直接回答**。面对自己不知道的事实，第一步是去查，而不是编。
- **计算交给了计算器工具**。LLM 做多位数乘法并不可靠，把确定性工作交给确定性工具。
- **每一步都有明确的「为什么」**。如果某一步的思考是「接下来随便试试」，通常意味着提示词设计出了问题。

## Agent 与邻近概念的边界

很多人把这几类东西混着叫，但它们的工程复杂度差一个数量级：

| 形态 | 控制流 | 典型成本 | 典型失败模式 |
| --- | --- | --- | --- |
| 提示词模板 | 代码 | 1 次调用 | 输出格式不稳 |
| RAG 问答 | 代码 | 1~2 次调用 | 检索不到就编答案 |
| 工具调用助手 | 代码（固定轮次） | 2~5 次调用 | 选错工具 |
| **Agent** | **模型** | 5~50+ 次调用 | 跑偏、死循环、成本失控 |
| 多 Agent 系统 | 模型 + 编排器 | 20~200+ 次调用 | 错误在角色间传播 |

:::callout warn 代价意识
表格右侧那列很重要：**控制权从代码交给模型的同时，稳定性、成本、可预测性都在下降**。所以一个务实的原则是——**能用固定流程解决的事，就不要交给 Agent**。只有当任务的路径无法预先枚举时，Agent 的自主性才值这个价。
:::

## 常见误区

:::callout danger 误区一：Agent 就是给 LLM 加几个工具
工具是必要条件，不是充分条件。真正让 Agent 成立的是「模型根据工具返回结果决定下一步」这个闭环。如果工具调用顺序由 `if/else` 决定，那你写的是一段带 LLM 的流程代码，不是 Agent。
:::

:::callout danger 误区二：Agent 越自主越好
自主性越高，可预测性越低。生产系统里常见的做法是**给自主性划边界**：允许模型在「检索策略」上自由发挥，但「写数据库」「发邮件」这类动作必须走确定性校验和审批。自主性应该是一个可调的旋钮，而不是一个开关。
:::

:::callout danger 误区三：效果不好就换个更强的模型
模型升级通常能解决 20% 的问题，剩下 80% 在提示结构、工具设计、状态管理、评估体系上。第 2、3 部分会逐项展开。
:::

## 本章要点

- Agent 的本质是**由模型掌握控制流的循环系统**，三条判据：自主决策、工具行动、闭环反馈。
- 最小定义只有三行伪代码，难点全在「怎么让决策可靠」「怎么让执行安全」「怎么让循环停止」。
- Agent 相对固定流程的代价是稳定性、成本与可预测性下降——**不要用它解决本来就有确定解法的问题**。

## 自测

1. 你正在做的一个功能是「用户上传合同 → 抽取双方名称与金额 → 存入数据库」。这是 Agent 吗？如果不是，改造成 Agent 会带来什么收益和风险？
2. 为什么说「控制流在谁手里」是区分 LLM 应用与 Agent 的核心标准？
3. 在你熟悉的业务里找出一个**路径无法预先枚举**的任务，说明它为什么适合交给 Agent。
