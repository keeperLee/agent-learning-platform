# 单 Agent vs 多 Agent 架构

多 Agent 是 Agent 领域被过度推销的概念之一。这一章的目标是给你一个**能抵御炒作**的判断框架：什么时候真的需要多 Agent，什么时候是在给自己挖坑。

## 先说不该拆的理由

:::callout danger 默认答案是"不拆"
一个能力足够的单 Agent + 良好的工具设计，能解决 80% 的场景。拆分多 Agent 会立刻带来四个成本：

1. **Token 成本成倍增长**。Agent 之间传递的上下文会重复计算，实测通常是单 Agent 的 3~10 倍。
2. **错误在角色间传播**。研究员检索错了，分析师、写作者会把这个错误一路放大成"逻辑自洽的错误结论"。
3. **调试难度指数上升**。单 Agent 的日志是一条线，多 Agent 的日志是一张图，且角色之间可能互相等待。
4. **延迟叠加**。串行的多 Agent 流水线，延迟是各环节之和。

**如果你不能用一句话说清"拆开之后哪个指标变好了"，那就不要拆。**
:::

## 什么信号说明"该拆了"

真正需要多 Agent 的信号，通常是下面这几条之一：

| 信号 | 说明 | 典型拆法 |
| --- | --- | --- |
| **上下文严重超载** | 单一 Agent 的工具/知识太多，提示词无法兼顾 | 按领域拆成多个专家 Agent |
| **需要不同"人格"或口径** | 例如"挑刺的审核者"和"创造性的写作者"难以共存于同一提示词 | 角色分离 |
| **子任务可并行** | 多个独立的检索/计算可以同时进行 | 并行 Worker + 汇总 |
| **需要交叉验证** | 结论必须由独立来源复核 | 生产者 + 审核者 |
| **权限边界不同** | 不同子任务需要不同的数据访问权限 | 按权限切分 |

注意：**前两条是真实需求，后三条要更谨慎**——它们往往能用单 Agent + 更好的工具设计解决。

## 四种常见拓扑

:::diagram multiAgent caption="图 11-1 · 左：单 Agent 串行执行；右：编排者 + 专家协作"
:::

### 一、主管制（Supervisor / Orchestrator）

一个编排者 + N 个专家 Worker。编排者负责拆解、派发、汇总。

```text
        Orchestrator
       ↙      ↓      ↘
  Researcher  Analyst  Writer
       ↘      ↓      ↙
         汇总结果
```

**优点**：结构清晰，职责单一，易于替换单个 Worker。
**缺点**：编排者是瓶颈和单点，它的判断质量决定全局。

### 二、流水线（Pipeline）

每个 Agent 的产物是下一个的输入，串行推进。

```text
抓取 → 抽取 → 校验 → 成文
```

**优点**：流程确定，可度量每个环节。
**缺点**：无回溯能力；前序出错后面全错。

:::callout warn 流水线其实常常不该用多 Agent
如果每个环节的任务是确定性的（比如"抽取字段"），用**代码 + 单次 LLM 调用**就够了，不需要独立 Agent。流水线的价值只在"每个环节都需要自主决策"时才成立。
:::

### 三、黑板（Blackboard）

所有 Agent 共享一块结构化区域（黑板），各自读写自己负责的部分。

```text
   ┌───────── 共享黑板 ─────────┐
   │ 目标 / 事实 / 待办 / 产物    │
   └────↑────────↑────────↑────┘
     Agent A   Agent B   Agent C
```

**优点**：解耦彻底，可以动态增减 Agent。
**缺点**：并发写入需要冲突解决；状态一致性难保证。

### 四、群聊（Debate / Group Chat）

多个 Agent 在同一个会话里轮流发言，通过讨论收敛。

**优点**：能产生真正的观点碰撞，适合需要权衡的决策问题。
**缺点**：最容易失控——容易陷入无休止的相互附和或争论，成本不可预测。

:::callout danger 群聊模式在生产环境要慎用
它看起来最"智能"，但实际上：① 收敛条件难定义（什么时候算讨论完了？）；② 成本随轮数平方增长；③ 参与者容易互相强化错误（"附和效应"）。

如果要用，必须设**硬性轮数上限 + 强制收敛条件 + 一个裁判角色**。
:::

## 通信：Agent 之间怎么交换信息

| 方式 | 描述 | 适用 |
| --- | --- | --- |
| **消息传递** | Agent 之间直接收发结构化消息 | 主管制、流水线 |
| **共享状态** | 通过共享的结构化对象读写 | 黑板 |
| **共享对话** | 同一个 messages 列表轮流追加 | 群聊 |

:::callout key 关键原则：传结构化数据，不传自然语言长文
```text
❌ 研究员 → 分析师：
   "我查了很多资料，找到一些关于市场规模的说明，大致上市场在增长，
    有几份报告提到了不同的数字……（300 字）"

✅ 研究员 → 分析师：
   {"findings": [{"metric": "市场规模", "value": "120-180 亿元",
                  "source": "RPT-2026-03", "note": "口径差异：含/不含 SaaS"},
                 ...],
    "confidence": 0.72, "gaps": ["缺少细分赛道数据"]}
```

**结构化传递带来三个好处**：token 消耗下降、解析不依赖语言理解、字段缺失能被程序立刻发现。
:::

## 成本与错误的量化

多 Agent 的账要算清楚。假设单 Agent 完成一个任务需要 8 次调用：

| 架构 | 调用次数 | 相对成本 | 错误传播风险 |
| --- | --- | --- | --- |
| 单 Agent | 8 | 1× | 低（线性） |
| 主管 + 2 Worker | ~22 | 2.8× | 中 |
| 主管 + 4 Worker + 审核 | ~40 | 5× | **中高**（审核能拦截部分） |
| 群聊 4 角色 × 5 轮 | ~80+ | 10×+ | 高 |

:::callout info 审核者角色的特殊价值
虽然审核者让成本上升，但它是唯一能**降低**错误传播风险的组件——因为它提供了一个"不从属于生产者"的判断视角。

如果只保留一个额外的 Agent，优先保留审核者，而不是多加一个生产者。
:::

## 决策清单

上多 Agent 之前，逐条自问：

- [ ] 单 Agent 是否真的试过了？上下文超载是"工具太多"还是"架构问题"？
- [ ] 拆开后，**哪个具体指标**会变好？（成本/延迟/准确率/可维护性）
- [ ] 拆开带来的 token 成本增长，业务能接受吗？
- [ ] Agent 之间的数据传递是结构化的吗？
- [ ] 有多少个角色？**超过 5 个就要重新审视**。
- [ ] 有全局的超时、步数与成本上限吗？
- [ ] 单个 Agent 失败时，整体是降级还是崩溃？
- [ ] 有一个能兜底的人工介入点吗？

:::callout key 一条经验法则
**优先增加工具，其次增加提示词约束，最后才增加 Agent。**

按这个顺序尝试，你会发现大多数"需要多 Agent"的场景，其实在第一步就解决了。
:::

## 本章要点

- **默认答案是"不拆"**：多 Agent 带来 3~10 倍成本、错误传播、调试难度和延迟。
- 真正该拆的信号：上下文超载、需要不同人格/口径、可并行的独立子任务、需要交叉验证、权限边界不同。
- 四种拓扑：**主管制、流水线、黑板、群聊**。群聊最需谨慎。
- Agent 之间要**传结构化数据**，不传自然语言长文。
- **如果只加一个额外 Agent，优先加审核者**（唯一能降低错误传播的角色）。
- 经验法则：**先加工具，再加约束，最后才加 Agent**。
