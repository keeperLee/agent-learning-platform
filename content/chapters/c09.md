# 上下文工程

前面几章讲的规划、记忆、工具，最终都要落到同一件事上：**把什么东西放进模型的上下文。**

所以有一句话说得很准：**在 Agent 里，你写的不是代码，你写的是上下文。**

## 上下文的六个组成部分

一个成熟 Agent 的上下文，通常由六块拼成，每块的成本和收益差别很大：

| 组成 | 典型占比 | 变化频率 | 优化空间 |
| --- | --- | --- | --- |
| 系统提示 / 角色规则 | 5~15% | 极低 | 低（但影响最大） |
| 工具定义（Schema） | 10~35% | 极低 | **高**（很多系统在这里浪费严重） |
| 长期记忆召回 | 5~15% | 每次不同 | 高 |
| 检索到的文档 | 0~40% | 每次不同 | **高** |
| 历史对话 | 10~40% | 累积增长 | **高** |
| 中间推理 / 工具结果 | 10~40% | 累积增长 | **高** |

把「工具定义」和「历史对话」都打开，再看 16K 窗口下的占比——**在 16K 窗口里，光是工具定义加历史对话就可能吃掉 40% 的预算，留给真正有用信息的空间被严重挤压。**

:::callout key 一个立刻可做的优化
如果你的 Agent 挂了 40 个工具，它们的 Schema 描述可能占掉 20K+ token，而且是**每次调用都要付这个成本**。

优化手段：① 精简描述，去掉冗余示例；② 按任务分组，只注入当前组；③ 用工具检索动态选 5~8 个。这个改动往往能把成本降 20% 以上，且不影响效果。
:::

## 位置效应：重要的东西放两头

"Lost in the middle" 是一个必须尊重的物理约束：**模型对上下文开头和结尾的注意力显著高于中间。**

```text title="推荐的上下文排布"
┌─────────────────────────────┐
│ ① 系统规则、安全约束、输出格式   │ ← 开头：高注意力，放"必须遵守"的规则
├─────────────────────────────┤
│ ② 工具定义                    │
├─────────────────────────────┤
│ ③ 历史对话摘要                 │ ← 中间：低注意力，放"参考性"内容
├─────────────────────────────┤
│ ④ 检索到的文档 / 证据          │
├─────────────────────────────┤
│ ⑤ 最近一轮工具结果             │
├─────────────────────────────┤
│ ⑥ 当前目标 + 待回答的问题      │ ← 结尾：高注意力，放"现在要做什么"
└─────────────────────────────┘
```

:::callout tip 一个立竿见影的改动
如果你只在系统提示开头写过一次目标，那么在多轮之后模型很可能"忘了"它在干什么。

**把原始目标在每一轮的末尾重述一次**，只是多花几十个 token，却能把跑偏率显著降低。这是投入产出比最高的一处改动。
:::

## 压缩：长会话的必修课

历史无限增长是 Agent 的必然结局。三种压缩手段，通常组合使用：

### 一、滚动摘要

```python {3-11} title="滚动摘要"
def rolling_summary(history, keep_recent=4, max_summary_tokens=400):
    recent = history[-keep_recent:]                 # 最近 4 轮保留原文（细节重要）
    older = history[:-keep_recent]
    if not older:
        return history
    summary = llm_summarize(
        older,
        instruction="保留：用户提出的约束、已确认的事实、未解决的问题、已完成的动作。"
                    "丢弃：寒暄、重复确认、失败的尝试细节。"
    )
    return [system(f"【前情摘要】{summary}"), *recent]
```

:::callout warn 摘要会丢信息，所以要"有选择地丢"
笼统地说"总结一下对话"会导致关键约束丢失。**必须显式告诉模型保留什么、丢弃什么**——这就是上面那段提示词的作用。

更稳妥的做法：摘要之外，另外维护一份**结构化的关键约束清单**（用户身份、硬性要求、禁止事项），这份清单永远不参与压缩。
:::

### 二、结构化提取

把冗长的工具返回提取成结构化字段，只保留后续推理需要的部分：

```python {2-6} title="工具结果的结构化压缩"
raw = fetch_order_details(order_id)      # 返回 8KB JSON，有 40 个字段
compact = {
    "order_id": raw["id"],
    "amount": raw["total_amount"],
    "status": raw["status"],
    "anomalies": extract_anomalies(raw),  # 只保留业务关心的异常项
}
# 8KB → 约 120 token
```

### 三、按需回查

如果信息当前用不到，就不要放进上下文——**记住它的 ID，需要时再取**：

```text title="延迟加载模式"
上下文里只放：  {"doc_id": "KB-2026-0831", "title": "差旅报销办法 v3.2", "relevance": 0.91}
模型需要细节时： 调用 read_document("KB-2026-0831", section="4")
```

:::callout key 延迟加载是把"上下文问题"转成"工具问题"
这是一种很优雅的思路：**不要试图把所有可能用到的信息预先塞进上下文，而是给模型一个"按需取回"的工具。**

代价是多一次往返调用，收益是上下文可以保持极简。
:::

## 提示结构：把期望显式化

Agent 的提示词和普通对话提示词的最大差别是：**必须显式写出"决策规则"，而不只是"角色设定"。**

```text {3-20} title="Agent 系统提示的推荐结构"
# 角色
你是数据分析 Agent，服务对象是公司内部运营人员。

# 可用数据的边界
- 你只能访问 analytics_readonly 库，禁止任何写操作。
- 用户只能查询自己部门的数据；跨部门请求一律拒绝并说明原因。

# 决策规则（按优先级）
1. 事实性问题必须先查数据，禁止凭记忆回答。
2. 涉及金额、日期、ID 的计算，必须使用 python_sandbox，不得口算。
3. 如果查询返回 0 行，先尝试放宽条件一次；仍为 0 则如实告知用户。
4. 如果用户请求超出职责范围，调用 transfer_to_human。

# 输出格式
- 结论前置，先给答案再给依据。
- 所有数字必须标注数据来源（表名 + 时间范围）。
- 单次回答不超过 5 句话；需要详细分析时输出结构化清单。

# 失败处理
工具连续失败 2 次时，停止重试，向用户说明遇到的问题并给出替代建议。
```

:::callout tip 三条写作原则
1. **用"必须 / 禁止"而不是"尽量 / 最好"**。模型对强约束的遵循度明显更高。
2. **给出优先级**。当规则冲突时，模型需要知道该听谁的。
3. **把边界写出来**。"超出范围时怎么办"和"正常情况怎么办"同样重要。
:::

## 一个反直觉的结论

:::callout warn 更长的提示词 ≠ 更好的效果
很多团队的第一反应是"效果不好 → 加规则 → 提示词越来越长"。但上下文里每多一条规则，都会稀释其他规则的注意力。

正确的迭代方式应该是：

1. **先看失败案例**，找出是**哪一类**问题；
2. **只针对这一类问题**加一条规则；
3. **跑评估集**，确认这一条确实带来了提升；
4. 如果没提升，**删掉它**。

提示词是要"做减法"的工程产物，不是越厚越好。（评估怎么做，见第 14 章。）
:::

## 本章要点

- 在 Agent 里，**你写的是上下文，不是代码**。上下文由六块组成，每块的成本收益不同。
- **位置效应**真实存在：规则放开头，目标放结尾。
- 压缩三种手段：**滚动摘要**（显式指定保留/丢弃）、**结构化提取**、**延迟加载（按需回查）**。
- 提示词要写出**决策规则与优先级**，而不只是角色设定。
- **上下文工程是做减法的工程**：加规则必须用评估验证，没提升就删。

第 2 部分到此结束。你已掌握 Agent 运转的五个核心机制。第 3 部分我们把这些机制组装成系统，从架构的高度看它们如何协同。
